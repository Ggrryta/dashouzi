# Blog 项目 Code Review 模块指南

> 目标：以 Code Review 方式吃透本项目**应该包含的所有技术要点**。
> 审查标尺不是"当前代码写对没有"，而是 **DESIGN.md 设计意图 + 行业最佳实践**。

---

## 一、审查方法论：5 步框架

每个模块走统一的 5 步，确保"读得懂、比得出、补得上、讲得清"：

```
① 读码  →  ② 对标  →  ③ 找差  →  ④ 补码  →  ⑤ 自测
 实际代码    设计意图    差距分析    理想实现    面试问答
```

| 步骤 | 做什么 | 产出 |
|---|---|---|
| ① 读码 | 逐行读实际实现，理解每行作用 | "代码现状"摘要 |
| ② 对标 | 对照 DESIGN.md + CHECKLIST.md + 最佳实践，列出"应该怎样" | "设计意图"清单 |
| ③ 找差 | 标注三类问题：**降级实现** / **未实现** / **潜在Bug** | 差距表 |
| ④ 补码 | 手写"理想版本"代码（关键是想清楚，不一定要能跑） | 补全代码 |
| ⑤ 自测 | 用 CHECKLIST 第十六节面试题自问自答，脱稿能讲 | 面试问答对 |

## 三、推荐审查顺序

按 **4 个阶段** 递进，遵循"先骨架后血肉、先业务后基础设施、先易后难"原则：

### 阶段一：架构骨架（理解整体，2 个模块）

```
① 三层架构与工程化  →  ② 认证授权
```

**为什么先看这两个**：
- ① 是整个项目的骨架，看懂分层 + 依赖注入，后面所有模块才能"挂"到正确的位置
- ② 认证授权是几乎所有业务模块的前置依赖（每条写操作都要先过 Auth + Role 中间件）
- 这两个实现质量较高，先建立"好的代码长什么样"的基准线

**阶段产出**：能画出请求从 HTTP 进来到 Service 执行的完整链路图

---

### 阶段二：业务核心（4 个模块，技术密度最高）

```
③ 文章状态机  →  ④ 点赞幂等  →  ⑤ DFA敏感词  →  ⑧ 评论树
```

**为什么这个顺序**：
- ③ 状态机：最简单的"用数据结构代替 if-else"范例，热身
- ④ 幂等：本项目最精妙的设计（事务 + ON CONFLICT），技术含量最高
- ⑤ DFA：独立算法模块，Trie 树是面试高频考点
- ⑧ 评论树：收尾业务逻辑，引出"树形数据如何存储与组装"

**阶段产出**：能脱稿讲清 4 个业务模块的核心算法和设计权衡

---

### 阶段三：基础设施与深度（4 个模块，差距最大）

```
⑥ 限流  →  ⑦ 全文搜索  →  ⑨ 统计聚合  →  Redis缓存(贯穿)
```

**为什么放这里**：
- ⑥⑦ 是本项目**差距最大**的两个模块（降级实现 + 完全未实现），code review 价值最高
- ⑨ 统计聚合 SQL 写得好，但能引出"N+1 查询""索引优化"等深度话题
- Redis 是贯穿性话题：限流要用、缓存要用、浏览量要用，但项目里**零实现**，作为独立专题补

**阶段产出**：能说清"生产级限流/搜索/缓存应该怎么做，本项目为什么降级"

---

### 阶段四：工程落地（2 个模块）

```
⑩ Docker部署  →  ⑪ 测试体系
```

**为什么最后看**：
- ⑩ Docker 相对简单，快速过一遍多阶段构建和 compose 编排
- ⑪ 测试体系项目里**完全缺失**，但面试必问，需要自己设计测试方案

**阶段产出**：能讲清"这个项目怎么部署、怎么测试、CI/CD 怎么搭"

## 六、如何使用本指南

1. **按推荐顺序**逐模块审查，每个模块走 5 步框架
2. 每完成一个模块，在 `REVIEW.md` 里按模板记录产出
3. 遇到"已知差距"标注的项，重点做 ④ 补码 练习
4. 全部完成后，用 CHECKLIST 第十六节面试题做总自测

### 单模块产出模板

```markdown
## 模块 X：[名称]

### ① 代码现状
（引用关键代码，标注 文件:行号）

### ② 设计意图
- DESIGN.md 说的：
- 最佳实践应该是：

### ③ 差距分析
| 差距类型 | 描述 | 严重程度 |

### ④ 理想实现
（手写补全代码）

### ⑤ 面试自测
- Q: ...?  A: ...
```
