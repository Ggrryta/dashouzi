# 限流设计专题文档

> 限流不是"挂个中间件"那么简单，不同场景的算法、阈值、粒度、失败策略都不同。
> 本文档以 **7 个业务情景** 为主线，每个情景给出业务背景、故障场景、限流方案与伪代码。
>
> 核心判断法则：**这个接口该不该允许突发**——该就用令牌桶，不该就用滑动窗口。

---

## 一、限流的本质

**限流 = 控制单位时间内的请求量，超过阈值的部分拒绝/排队/降级。**

目的不是"不让用"，而是"防止局部过载拖垮整体"。

### 四层限流体系

```
请求 → ① 网关层    全局 QPS / 并发连接数    防 DDoS/CC
       → ② 应用层   按接口/用户/IP 限流      防单用户滥用
          → ③ 服务层  下游 RPC 调用频率       防雪崩
             → ④ 资源层  DB/Redis 连接池      保护后端
```

本文重点讲第②层（应用层），兼顾①③。

---

## 二、四种核心算法

在看情景前，先理解四种算法——不同场景选不同算法。

### 算法 1：固定窗口（Fixed Window）

```
每分钟一个窗口，窗口内计数，到点重置
  0:00 ──────── 0:59 │ 1:00 ──────── 1:59
  count=20            count=0(重置)
```

- **实现**：`count++`，到窗口结束清零
- **优点**：最简单
- **缺点**：**窗口边界突刺**——0:59 来 20 个 + 1:01 来 20 个 = 2 秒内 40 个

### 算法 2：滑动窗口（Sliding Window）

```
统计"过去 60 秒内"的请求数，窗口随时间滑动
  当前时刻往前推 60 秒，数这个范围内的请求
```

- **实现**：Redis ZSET 存每次请求时间戳，`ZREMRANGEBYSCORE` 清过期 + `ZCARD` 计数
- **优点**：消除边界突刺
- **缺点**：每个请求存一条记录，内存开销比固定窗口大

### 算法 3：令牌桶（Token Bucket）

```
桶以固定速率放令牌，请求消耗令牌，桶满则溢出丢弃
  放令牌：每秒 10 个
  桶容量：20（可攒突发）
  请求来了：有令牌就消耗1个放行，没有就拒绝
```

- **实现**：记录"上次取令牌时间 + 当前令牌数"，每次请求计算应补充的令牌
- **优点**：**支持突发**——平时攒令牌，突发时一次性消耗多个
- **缺点**：实现比滑动窗口复杂

### 算法 4：漏桶（Leaky Bucket）

```
请求像水滴进桶，桶以恒定速率漏水（处理请求），满了则溢出（拒绝）
  漏水速率：每秒 10 个（恒定处理速率）
  桶容量：100（排队缓冲）
```

- **实现**：队列 + 恒定消费速率
- **优点**：**匀速整形**——不管请求多突发，下游处理速率恒定
- **缺点**：不允许突发，正常用户体验差

### 四种算法对比

| 算法 | 突发支持 | 实现复杂度 | 适用场景 |
|------|:-------:|:---------:|---------|
| 固定窗口 | ❌ 有突刺 | ★ | 粗粒度、不在意突刺 |
| 滑动窗口 | ❌ 严格 | ★★ | 不该有突发的场景（登录/评论） |
| 令牌桶 | ✅ | ★★★ | 允许偶发突发的场景（搜索/点赞） |
| 漏桶 | ❌ 匀速 | ★★ | 保护下游、匀速整形（全局/网关） |

### 情景一：登录防暴力破解（IP 级，滑动窗口）

#### 业务背景

黑客用字典撞库，对 `/login` 接口高频尝试不同密码。登录接口是未认证的，只能按 IP 限流。

#### 业务需求

- 单个 IP 每分钟最多 30 次登录请求
- 超过返回 429
- 不允许突发——撞库就是均匀高频，不该放行任何突发

#### 不做限流会怎样

```
黑客脚本每秒发 100 次登录请求
→ 密码哈希计算（bcrypt）极耗 CPU
→ 登录接口拖垮整个服务，正常用户无法登录
```

#### 限流方案：滑动窗口（Redis ZSET）

不允许突发，用滑动窗口严格限制。项目已有此实现。

#### 伪代码

```go
// Lua 脚本：ZSET 滑动窗口（项目 ratelimit.go 已实现）
const slidingWindowLua = `
local key    = KEYS[1]
local now    = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit  = tonumber(ARGV[3])
local member = ARGV[4]

-- 移除窗口外过期请求
redis.call('ZREMRANGEBYSCORE', key, '-inf', now - window)
-- 统计窗口内请求数
local count = redis.call('ZCARD', key)

if count < limit then
    redis.call('ZADD', key, now, member)
    redis.call('PEXPIRE', key, window + 1000)
    return 1  -- 放行
else
    return 0  -- 拒绝
end
`

// 中间件：按 IP 限流
func RateLimit(limiter Limiter) gin.HandlerFunc {
    return func(c *gin.Context) {
        key := fmt.Sprintf("rl:ip:%s:%s", c.ClientIP(), c.Request.URL.Path)
        allowed, err := limiter.Allow(c.Request.Context(), key)
        if err != nil {
            c.Next() // fail-open
            return
        }
        if !allowed {
            response.Error(c, errcode.ErrRateLimited) // 429
            c.Abort()
            return
        }
        c.Next()
    }
}

// 路由挂载
rateLimit.Use(RateLimit(NewRedisLimiter(rdb, 30, time.Minute)))
```

#### 关键点

- **按 IP 限流**：未认证接口没有 user_id，只能按 IP
- **滑动窗口而非固定窗口**：防止窗口边界 2x 突刺
- **Lua 脚本保证原子性**：多实例下安全
- **进阶**：连续失败 N 次后加验证码或锁定账号

### 情景二：评论防灌水（用户级，滑动窗口）

#### 业务背景

机器人注册账号后批量发垃圾评论。评论是已认证写操作，可以按 user_id 精确限流。

#### 业务需求

- 单个用户每分钟最多 20 条评论
- 超过返回 429
- 不允许突发——灌水就是批量发，不该放行

#### 不做限流会怎样

```
机器人每秒发 50 条评论
→ 评论表被灌满垃圾数据
→ 敏感词过滤（DFA）被高频调用，CPU 飙升
```

#### 限流方案：滑动窗口（按 user_id）

和登录一样的滑动窗口算法，区别是 key 按 user_id 而非 IP。项目已有此实现。

#### 伪代码

```go
// 中间件：已认证按 user_id，未认证按 IP
func RateLimit(limiter Limiter) gin.HandlerFunc {
    return func(c *gin.Context) {
        var key string
        if uid, exists := c.Get("user_id"); exists {
            key = fmt.Sprintf("rl:u:%v:%s", uid, c.Request.URL.Path) // 按用户
        } else {
            key = fmt.Sprintf("rl:ip:%s:%s", c.ClientIP(), c.Request.URL.Path) // 按 IP
        }
        allowed, _ := limiter.Allow(c.Request.Context(), key)
        if !allowed {
            response.Error(c, errcode.ErrRateLimited)
            c.Abort()
            return
        }
        c.Next()
    }
}

// 路由：评论 20次/分钟
commentAuth.Use(RateLimit(NewRedisLimiter(rdb, 20, time.Minute)))
```

#### 关键点

- **按 user_id 而非 IP**：已认证用户精确到人，比 IP 更准（NAT 后多用户共一个 IP）
- **阈值比登录更严**：20 < 30，因为评论是 UGC 写操作，价值低风险高
- **按路径区分 key**：用户对评论的配额不影响他对点赞的使用

### 情景三：搜索防爬虫（令牌桶，允许突发）

#### 业务背景

用户搜索文章，接口走 `ILIKE '%kw%'` 全表扫描。正常用户偶尔搜几次，爬虫高频抓取。当前项目**没有**给搜索限流。

#### 业务需求

- 单个用户每分钟最多 100 次搜索
- **允许突发**——正常用户连续翻页搜索不该被拦
- 爬虫匀速高频请求要被挡住

#### 不做限流会怎样

```
爬虫每秒发 200 次搜索
→ 每次 ILIKE 全表扫描
→ DB CPU 100%，所有查询超时
→ 全站卡死
```

#### 限流方案：令牌桶（支持突发）

搜索场景**该允许突发**（用户连续搜索是正常行为），所以用令牌桶而非滑动窗口。

#### 伪代码

```go
// Redis 令牌桶 Lua 脚本
const tokenBucketLua = `
local key         = KEYS[1]
local now         = tonumber(ARGV[1])       -- 当前毫秒时间戳
local capacity    = tonumber(ARGV[2])       -- 桶容量（突发上限）
local refillRate  = tonumber(ARGV[3])       -- 每毫秒补充令牌数
local requested   = tonumber(ARGV[4])       -- 本次请求消耗令牌数（通常1）

-- 读取当前状态
local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens    = tonumber(bucket[1]) or capacity
local lastTime  = tonumber(bucket[2]) or now

-- 计算这段时间应补充的令牌
local delta = now - lastTime
local refilled = tokens + delta * refillRate
if refilled > capacity then refilled = capacity end

-- 判断是否够令牌
if refilled >= requested then
    refilled = refilled - requested
    redis.call('HMSET', key, 'tokens', refilled, 'last_refill', now)
    redis.call('PEXPIRE', key, 60000)  -- 1分钟不活跃则过期
    return 1  -- 放行
else
    redis.call('HMSET', key, 'tokens', refilled, 'last_refill', now)
    redis.call('PEXPIRE', key, 60000)
    return 0  -- 拒绝
end
`

type tokenBucketLimiter struct {
    client   *redis.Client
    capacity int           // 桶容量：突发上限
    rate     float64       // 每秒补充令牌数
    script   *redis.Script
}

func NewTokenBucketLimiter(client *redis.Client, capacity int, ratePerSec float64) Limiter {
    return &tokenBucketLimiter{
        client:   client,
        capacity: capacity,
        rate:     ratePerSec,
        script:   redis.NewScript(tokenBucketLua),
    }
}

func (l *tokenBucketLimiter) Allow(ctx context.Context, key string) (bool, error) {
    // capacity=100（可攒100个突发）, rate=100/60≈1.67/s（每秒补1.67个令牌）
    result, err := l.script.Run(ctx, l.client,
        []string{key},
        time.Now().UnixMilli(),
        l.capacity,
        l.rate / 1000,  // 转成每毫秒
        1,              // 消耗1个令牌
    ).Int()
    if err != nil {
        return false, err
    }
    return result == 1, nil
}

// 路由：搜索 100次/分钟，桶容量100（允许突发100次）
searchGroup.Use(RateLimit(NewTokenBucketLimiter(rdb, 100, 100.0/60)))
```

#### 令牌桶 vs 滑动窗口的行为差异

```
用户 1 秒内连发 80 次搜索：
  滑动窗口（100/min）：窗口内80 < 100 → 全放行... 但第101次会被拒
  令牌桶（容量100，补1.67/s）：
    开始有100令牌，80次消耗后剩20
    第81次：有令牌 → 放行
    ...
    连发到100次时令牌耗尽 → 第101次拒绝
    但等0.6秒后补了1个令牌 → 又能搜了
```

令牌桶允许"短时爆发后恢复"，滑动窗口是"窗口内硬上限"。

#### 关键点

- **允许突发**：正常用户连续搜索不该被拦
- **桶容量 = 突发上限**：设100表示最多连发100次
- **补充速率 = 平均限制**：100/分钟表示平均每分钟100次
- **项目缺失**：搜索是 ILIKE 全表扫描，最该加限流却没加

### 情景四：文章创建防批量（长窗口 + 低阈值）

#### 业务背景

机器人注册 author 账号后批量创建垃圾文章。文章创建是低频高价值操作，正常用户一天发几篇，机器人一小时发几百篇。当前项目**没有**给文章创建限流。

#### 业务需求

- 单个用户每小时最多 10 篇文章
- 允许偶尔连发（写完一篇接着发第二篇）
- 严格限制批量创建

#### 不做限流会怎样

```
机器人每小时发 500 篇文章
→ articles 表灌满垃圾
→ generateSlug（纳秒+随机）高并发碰撞
→ 敏感词过滤被高频调用
```

#### 限流方案：令牌桶（长窗口 + 低阈值）

用令牌桶，桶容量小（允许偶尔连发2-3篇），补充速率极低（每小时10个令牌）。

#### 伪代码

```go
// 文章创建：每小时10篇，桶容量3（允许偶尔连发3篇）
auth.POST("/articles",
    middleware.Role("author"),
    middleware.RateLimit(NewTokenBucketLimiter(rdb, 3, 10.0/3600)), // 容量3, 10篇/小时
    articleHandler.Create,
)
```

#### 关键点

- **长窗口 + 低阈值**：10/小时 而非 10/分钟，因为发文是低频操作
- **桶容量小**：3 表示最多连发3篇，防止一次性灌一批
- **令牌桶而非滑动窗口**：允许写完一篇紧接着发第二篇（突发）

### 情景五：全局限流保护系统（网关层，漏桶）

#### 业务背景

CC 攻击不分用户不分接口，整体 QPS 飙到 5000，单个应用实例扛不住。前面的用户级限流挡不住分布式攻击（每个攻击源频率都不高，但总量巨大）。

#### 业务需求

- 全局总 QPS 不超过 1000
- 超过的请求排队或拒绝
- **匀速整形**——不管来多猛，下游处理速率恒定

#### 不做限流会怎样

```
CC 攻击 5000 QPS 打进来
→ 用户级限流每个key都不超限（分布式攻击每个源频率低）
→ 但总量 5000 QPS 打爆 DB
→ 全站不可用
```

#### 限流方案：漏桶（匀速整形）

全局限流的目标是"不管请求多猛，下游处理速率恒定"，用漏桶最合适。通常在网关层（Nginx）做。

#### 伪代码

```nginx
# Nginx 漏桶限流（limit_req 模块）
# 每秒处理 1000 个请求，缓冲队列 500
limit_req_zone $binary_remote_addr zone=global:10m rate=1000r/s;

server {
    location /api/ {
        limit_req zone=global burst=500 nodelay;
        # burst=500: 超出速率的请求最多排队500个
        # nodelay: 不延迟，超过burst直接拒绝
        proxy_pass http://backend;
    }
}
```

如果要在应用层做全局限流（无 Nginx）：

```go
// 应用层漏桶：全局共享一个限流器，key 固定
func GlobalRateLimit(limiter Limiter) gin.HandlerFunc {
    return func(c *gin.Context) {
        // 所有请求共享同一个 key "global"
        allowed, _ := limiter.Allow(c.Request.Context(), "global")
        if !allowed {
            response.Error(c, errcode.ErrRateLimited)
            c.Abort()
            return
        }
        c.Next()
    }
}

// 全局 1000 QPS，挂在最外层
r.Use(GlobalRateLimit(NewRedisLimiter(rdb, 1000, time.Second)))
```

#### 关键点

- **全局限流在用户限流之前**：先全局挡总量，再用户级防单用户
- **网关层做最合适**：Nginx `limit_req` 性能远高于应用层
- **漏桶匀速整形**：保护下游不被突发打垮
- **项目缺失**：无全局限流，CC 攻击可直接穿透

### 情景六：下游服务调用限流（熔断 + 限流配合）

#### 业务背景

微服务架构下，服务 A 调用服务 B。B 突然变慢（DB 抖动），A 的请求堆积在等待 B 的响应，A 的线程池耗尽，A 也挂了——雪崩。

#### 业务需求

- 对下游 B 的调用限流：每秒最多 100 次
- B 故障率超阈值时**熔断**，直接快速失败不再调用
- B 恢复后自动半开探测

#### 不做限流会怎样

```
服务B变慢（响应从10ms变2s）
→ 服务A等待B的响应，线程池被占满
→ A也无法服务其他请求
→ 雪崩扩散到依赖A的所有服务
```

#### 限流方案：限流 + 熔断器配合

限流控制正常情况下的调用频率；熔断器在下游故障时快速失败，避免线程堆积。

#### 伪代码

```go
// 熔断器状态机：closed → open → half-open → closed
type CircuitBreaker struct {
    mu            sync.Mutex
    state         string   // closed / open / half-open
    failureCount  int
    threshold     int      // 连续失败阈值
    openUntil     time.Time
    cooldown      time.Duration
}

func (cb *CircuitBreaker) Allow() bool {
    cb.mu.Lock()
    defer cb.mu.Unlock()

    switch cb.state {
    case "closed":
        return true // 正常放行
    case "open":
        if time.Now().After(cb.openUntil) {
            cb.state = "half-open" // 冷却期过，半开探测
            return true
        }
        return false // 熔断中，快速失败
    case "half-open":
        return true // 放一个请求探测
    }
    return true
}

func (cb *CircuitBreaker) RecordSuccess() {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    cb.failureCount = 0
    cb.state = "closed" // 探测成功，恢复
}

func (cb *CircuitBreaker) RecordFailure() {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    cb.failureCount++
    if cb.failureCount >= cb.threshold {
        cb.state = "open"
        cb.openUntil = time.Now().Add(cb.cooldown) // 熔断冷却期
    }
}

// 调用下游：先限流 + 再熔断
func (c *ServiceAClient) CallB(ctx context.Context, req Request) (Response, error) {
    // 1. 限流：控制调用频率
    allowed, _ := c.rateLimiter.Allow(ctx, "call_service_b")
    if !allowed {
        return Response{}, ErrRateLimited
    }

    // 2. 熔断：下游故障时快速失败
    if !c.breaker.Allow() {
        return Response{}, ErrCircuitOpen // 不等下游，直接返回
    }

    // 3. 实际调用
    resp, err := c.client.Call(ctx, req)
    if err != nil {
        c.breaker.RecordFailure()
        return resp, err
    }
    c.breaker.RecordSuccess()
    return resp, nil
}
```

#### 关键点

- **限流管正常频率，熔断管故障降级**：两者配合
- **熔断三态**：closed（正常）→ open（故障快速失败）→ half-open（探活恢复）
- **快速失败防雪崩**：不等慢下游，直接返回错误，释放线程
- **自动恢复**：冷却期后半开探测，成功则恢复

### 情景七：文件上传限流（按字节限速）

#### 业务背景

用户上传头像/封面图，大文件消耗带宽。不限速的话几个大文件同时上传会占满带宽，影响其他用户。

#### 业务需求

- 单个用户上传带宽限制：1MB/s
- 限制并发上传数：同时最多 2 个
- 不按请求数限流，按**字节流量**限流

#### 不做限流会怎样

```
用户同时上传 5 个 100MB 文件
→ 带宽被占满
→ 其他用户请求超时
```

#### 限流方案：令牌桶（按字节发令牌）

和 QPS 限流的令牌桶一样，区别是令牌的单位是**字节**而非请求数。

#### 伪代码

```go
// 字节级令牌桶：每秒补充 1MB 令牌，桶容量 2MB（允许短时突发）
type byteRateLimiter struct {
    client   *redis.Client
    capacity int64       // 桶容量（字节）：2MB
    rate     float64     // 每秒补充字节：1MB
    script   *redis.Script
}

func (l *byteRateLimiter) AllowBytes(ctx context.Context, key string, bytes int64) (bool, error) {
    // 和令牌桶逻辑一样，但消耗的令牌数 = 本次上传字节数
    result, err := l.script.Run(ctx, l.client,
        []string{key},
        time.Now().UnixMilli(),
        l.capacity,
        l.rate / 1000,
        bytes,  // ← 消耗 N 个令牌（N=字节数）
    ).Int()
    return result == 1, err
}

// 上传 handler
func UploadCover(c *gin.Context) {
    userID := c.GetUint("user_id")
    file, _ := c.FormFile("cover")

    // 按字节限流
    allowed, _ := byteLimiter.AllowBytes(c.Request.Context(),
        fmt.Sprintf("upload:%d", userID),
        file.Size, // 消耗的令牌数 = 文件大小
    )
    if !allowed {
        response.Error(c, errcode.ErrUploadRateLimited)
        return
    }

    c.SaveUploadedFile(file, path)
}
```

#### 关键点

- **限字节而非限请求数**：一个 100MB 文件和一个 10KB 文件的"代价"不同
- **令牌桶按字节发**：每秒补 1MB 令牌，消耗按文件大小
- **并发限制**：可用 Redis INCR 限制同时上传数

## 四、算法选型决策树

```
该接口该不该允许突发？
├─ 不该（严格限制）→ 滑动窗口
│   ├─ 登录/注册（防暴破）
│   └─ 评论/发帖（防灌水）
│
├─ 该（允许偶发连发）→ 令牌桶
│   ├─ 搜索（正常用户连续搜索）
│   ├─ 点赞/收藏（浏览时连续操作）
│   └─ 文章创建（偶尔连发两三篇）
│
└─ 要匀速整形（保护下游）→ 漏桶
    ├─ 全局限流（网关层）
    └─ 下游调用限流（匀速发给下游）
```

## 六、多级限流策略

生产系统通常不是单一限流，而是**多级叠加**：

```
请求进来
  │
  ├─ 第1级：网关全局限流（漏桶 1000 QPS）
  │    → 挡住总量，防 CC/DDoS
  │
  ├─ 第2级：接口级限流（按接口不同算法不同阈值）
  │    → 登录30/min（滑动窗口）
  │    → 评论20/min（滑动窗口）
  │    → 搜索100/min（令牌桶）
  │
  ├─ 第3级：用户级限流（user_id 维度）
  │    → 防单用户滥用
  │
  └─ 第4级：资源级限流（连接池/线程池）
       → DB 连接池上限 50
       → 保护后端不被打爆
```

**先粗后细**：先全局挡总量，再接口级分策略，最后用户级防个人。每层挡掉不同维度的风险。

## 七、失败策略：被限流后怎么办

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **直接拒绝** | 返回 429 | 大多数 API 限流 |
| **排队等待** | 请求进队列，匀速处理 | 对延迟不敏感的场景 |
| **降级返回** | 返回缓存/默认值 | 读操作（搜索返回热门结果） |
| **fail-open** | 限流器故障时放行 | 限流不能拖垮核心链路 |

项目当前用"直接拒绝 + fail-open"——Redis 故障时放行，避免限流依赖拖垮服务。这是合理的默认策略，但对防攻击场景不够（fail-open 会让攻击穿透）。
