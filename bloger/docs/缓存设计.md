# Redis 缓存设计专题文档

> 缓存是后端性能优化的第一手段：用内存换时间，用空间换性能。
> 本文档以 **7 个情景** 为主线讲缓存怎么用，再单独深入 **数据一致性** 和 **缓存三剑客** 两大专题。
>
> 核心法则：**读多写少用 Cache-Aside，写多容忍丢失用 Write-Behind，强一致用 Write-Through。**

---

## 一、缓存的本质与三种模式

### 为什么需要缓存

```
无缓存：每次请求 → 查 DB（磁盘 IO + SQL 解析 + JOIN）→ 10ms
有缓存：第一次查 DB 写缓存 → 后续请求 → 查 Redis（内存）→ 0.1ms
```

DB 查询要走磁盘 IO、SQL 解析、可能多表 JOIN，毫秒级；Redis 纯内存操作，亚毫秒级。缓存让热点数据的读取快 100 倍。

### 三种缓存模式

| 模式 | 读 | 写 | 一致性 | 适用 |
|------|-----|-----|:------:|------|
| **Cache-Aside** | 查缓存→未命中查DB→写缓存 | 更新DB→删缓存 | 最终一致 | 读多写少 |
| **Write-Through** | 只查缓存 | 同时写缓存+DB | 强一致 | 一致性要求高 |
| **Write-Behind** | 只查缓存 | 只写缓存→异步回写DB | 弱一致 | 写多容忍丢失 |

```
Cache-Aside（旁路）：      Write-Through（穿透）：    Write-Behind（写回）：
  读：缓存→DB→回填          读：只查缓存              读：只查缓存
  写：DB→删缓存             写：缓存+DB 同步          写：只写缓存→异步回DB
  最常用                    强一致但写慢              写最快但会丢数据
```

### 情景一：文章详情缓存（Cache-Aside）

#### 业务背景

博客文章详情页是系统最高频的读接口。每次查询要 `Preload("Tags").Preload("Author")`，两个 JOIN，DB 压力大。

#### 业务需求

- 文章详情查询 < 1ms
- 文章更新后用户能很快看到新内容
- DB 不被高频读请求打垮

#### 缓存方案：Cache-Aside + 主动失效

```go
type ArticleService struct {
    rdb        *redis.Client
    articleRepo repository.ArticleRepository
}

// 读：先缓存后 DB
func (s *ArticleService) GetPublicByID(ctx context.Context, id uint) (*model.Article, error) {
    key := fmt.Sprintf("article:public:%d", id)

    // 1. 查缓存
    if cached, err := s.rdb.Get(ctx, key).Bytes(); err == nil {
        if string(cached) == "NULL" {
            return nil, ErrArticleNotFound // 缓存空值（防穿透）
        }
        var article model.Article
        json.Unmarshal(cached, &article)
        return &article, nil
    }

    // 2. 未命中，查 DB
    article, err := s.articleRepo.FindByID(ctx, id)
    if err != nil || article == nil || article.Status != "published" {
        s.rdb.Set(ctx, key, "NULL", 1*time.Minute) // 缓存空值，短 TTL
        return nil, ErrArticleNotFound
    }
    s.articleRepo.IncrementViewCount(ctx, id)

    // 3. 写缓存（带 TTL + 随机抖动防雪崩）
    data, _ := json.Marshal(article)
    ttl := 10*time.Minute + time.Duration(rand.Intn(120))*time.Second
    s.rdb.Set(ctx, key, data, ttl)
    return article, nil
}

// 写：更新 DB 后删缓存
func (s *ArticleService) Update(ctx context.Context, userID uint, role string, articleID uint, input UpdateArticleInput) error {
    // ... 校验 + 更新 DB ...
    err := s.runInTx(ctx, func(ar, tr) error {
        // ... 更新文章 ...
        return ar.Update(ctx, article)
    })
    if err != nil {
        return err
    }

    // 删缓存（让下次读时回源 DB 拿新数据）
    s.rdb.Del(ctx, fmt.Sprintf("article:public:%d", articleID))
    return nil
}
```

#### 数据一致性保证

采用"**先更新 DB，再删缓存**"策略：
- 更新 DB 后删缓存，下次读时会回源 DB 拿到最新数据
- 不更新缓存而选择删除：避免并发更新导致缓存和 DB 不一致
- 配合 TTL 兜底：即使删缓存失败，TTL 到期后缓存也会自动失效

#### 关键点

- **缓存对象序列化**：用 JSON 序列化存 Redis，读时反序列化
- **TTL 加随机抖动**：`10min + rand(0~120s)`，防止大量 key 同时过期（防雪崩）
- **缓存空值**：不存在的文章也缓存 `"NULL"`，防穿透
- **删缓存而非更新缓存**：避免并发写导致脏数据

### 情景二：浏览量统计（Write-Behind）

#### 业务背景

文章每次被访问 `view_count + 1`。当前同步 `UPDATE articles SET view_count = view_count + 1`，高并发下每次访问都写 DB，是性能瓶颈。

#### 业务需求

- 浏览量实时增长
- DB 不被高频写打垮
- 可容忍极小概率数据丢失（Redis 宕机丢几秒数据）

#### 缓存方案：Write-Behind（只写缓存，定时回写）

```go
// 读文章时：浏览量写 Redis，不碰 DB
func (s *ArticleService) GetPublicByID(ctx context.Context, id uint) (*model.Article, error) {
    article := ... // 查文章（走缓存或 DB）

    // 浏览量写 Redis，不写 DB
    s.rdb.Incr(ctx, fmt.Sprintf("view_count:%d", id))
    article.ViewCount++ // 内存里 +1 返回给用户
    return article, nil
}

// 定时任务：每分钟批量回写 DB
func (s *ArticleService) FlushViewCounts(ctx context.Context) {
    // 扫描所有 view_count:* 的 key
    keys, _ := s.rdb.Keys(ctx, "view_count:*").Result()

    pipe := s.rdb.Pipeline()
    for _, key := range keys {
        pipe.Get(ctx, key)
    }
    results, _ := pipe.Exec(ctx)

    // 批量回写 DB
    for i, key := range keys {
        articleID := parseArticleID(key) // 从 key 提取 ID
        incr, _ := results[i].(*redis.StringCmd).Int64()

        s.articleRepo.BatchIncrementViewCount(ctx, articleID, incr)
        s.rdb.Del(ctx, key) // 回写后清零
    }
}

// repository
func (r *articleRepo) BatchIncrementViewCount(_ context.Context, id uint, incr int64) error {
    return r.db.Model(&model.Article{}).Where("id = ?", id).
        UpdateColumn("view_count", gorm.Expr("view_count + ?", incr)).Error
}
```

#### 数据一致性

- **弱一致**：Redis 里的浏览量和 DB 有最多 1 分钟延迟
- **丢数据风险**：Redis 宕机未回写的数据会丢失（可接受，浏览量不要求精确）
- **兜底**：回写后立即 `Del` key，防止下次回写重复加

#### 关键点

- **INCR 原子**：Redis 的 INCR 是原子的，高并发安全
- **批量回写**：每分钟一次批量 UPDATE，而非每次访问一次
- **Pipeline 减少 RTT**：用 Pipeline 批量 GET，减少网络往返
- **容忍丢失**：浏览量不是金融数据，丢几秒可接受

### 情景三：热门文章排行榜（ZSET）

#### 业务背景

首页展示热门文章榜，按浏览量排序。当前每次 `ORDER BY view_count DESC` 查 DB，数据量大时排序慢。

#### 业务需求

- 实时更新排行（文章被浏览后排名变化）
- 取 Top N 要快
- 不用每次排序

#### 缓存方案：Redis ZSET（天然有序）

```go
// 文章被浏览时，ZSET 分数 +1
func (s *ArticleService) RecordView(ctx context.Context, articleID uint) {
    s.rdb.ZIncrBy(ctx, "trending:articles", 1, fmt.Sprintf("%d", articleID))
}

// 排行榜：ZREVRANGE 取 Top N
func (s *ArticleService) Trending(ctx context.Context, limit int) ([]*model.Article, error) {
    // 1. 从 ZSET 取 Top N 的文章 ID（按分数降序）
    ids, _ := s.rdb.ZRevRange(ctx, "trending:articles", 0, int64(limit-1)).Result()

    // 2. 批量查文章详情（走文章缓存）
    var articles []*model.Article
    for _, idStr := range ids {
        id, _ := strconv.ParseUint(idStr, 10, 64)
        a, _ := s.GetPublicByID(ctx, uint(id)) // 走缓存
        if a != nil {
            articles = append(articles, a)
        }
    }
    return articles, nil
}

// 定时清理：只保留 Top 100，避免 ZSET 无限增长
func (s *ArticleService) TrimTrending(ctx context.Context) {
    s.rdb.ZRemRangeByRank(ctx, "trending:articles", 0, -101) // 删掉排名100之后的
}
```

#### 为什么用 ZSET

| 方式 | 取 Top N | 更新分数 | 排序 |
|------|---------|---------|------|
| DB ORDER BY | O(N log N) 扫表 | UPDATE 一次 | 每次查都排 |
| Redis ZSET | O(log N) | ZINCRBY O(log N) | 自动维护有序 |

ZSET 内部是跳表（SkipList），插入和取 Top N 都是 O(log N)，比 DB 每次排序快得多。

#### 数据一致性

- ZSET 的分数（浏览量）和 DB 的 view_count 可能短暂不一致
- 可定时用 ZSET 的分数回写 DB 的 view_count（和情景二合并）
- 排行榜不要求精确，延迟可接受

#### 关键点

- **ZINCRBY 原子**：并发浏览安全
- **ZREVRANGE**：按分数降序取 N 个，O(log N + M)
- **定期清理**：ZRemRangeByRank 删掉排名靠后的，控制 ZSET 大小

### 情景四：标签列表缓存（Cache-Aside，长 TTL）

#### 业务背景

文章列表页每条文章都 Preload Tags。标签很少变（只有创建文章时可能新增标签），但每次查文章列表都要 JOIN 标签表。

#### 业务需求

- 标签列表查询极快
- 标签变更后能及时更新
- 标签数据量小，适合全量缓存

#### 缓存方案：Cache-Aside + 长 TTL + 主动失效

```go
func (s *ArticleService) ListTags(ctx context.Context) ([]*model.Tag, error) {
    key := "tags:all"

    // 1. 查缓存
    if cached, err := s.rdb.Get(ctx, key).Bytes(); err == nil {
        var tags []*model.Tag
        json.Unmarshal(cached, &tags)
        return tags, nil
    }

    // 2. 查 DB
    tags, err := s.tagRepo.List(ctx)
    if err != nil {
        return nil, err
    }

    // 3. 写缓存（标签不常变，缓存 1 小时）
    data, _ := json.Marshal(tags)
    s.rdb.Set(ctx, key, data, 1*time.Hour)
    return tags, nil
}

// 创建文章时可能新增标签 → 删标签缓存
func (s *ArticleService) Create(ctx context.Context, authorID uint, input CreateArticleInput) (*model.Article, error) {
    // ... 创建文章（含 FindOrCreate 标签）...
    err := s.runInTx(ctx, func(ar, tr) error {
        for _, name := range input.TagNames {
            tr.FindOrCreate(ctx, name) // 可能新建标签
        }
        return ar.Create(ctx, article)
    })
    if err != nil {
        return nil, err
    }

    // 删标签缓存（下次读时回源）
    s.rdb.Del(ctx, "tags:all")
    return article, nil
}
```

#### 数据一致性

- 标签变更频率极低（只有新建文章且标签不存在时才新增）
- 1 小时 TTL + 主动删缓存，双重保障
- 即使删缓存失败，最多 1 小时后自动过期

#### 关键点

- **长 TTL**：标签不常变，1 小时足够
- **数据量小全量缓存**：标签通常几十个，JSON 序列化后几 KB
- **创建文章时删缓存**：FindOrCreate 可能新增标签，要失效

### 情景五：点赞状态缓存（Cache-Aside，短 TTL）

#### 业务背景

前端展示"用户是否已点赞"按钮状态，每次访问文章都要查。当前 `IsLiked` 每次查 DB 的 likes 表。

#### 业务需求

- 点赞状态查询 < 1ms
- 点赞/取消后状态及时更新
- 可容忍短暂不一致（几秒）

#### 缓存方案：Cache-Aside + 短 TTL + Toggle 时删缓存

```go
func (s *LikeService) IsLiked(ctx context.Context, userID uint, targetType string, targetID uint) (bool, error) {
    key := fmt.Sprintf("liked:%d:%s:%d", userID, targetType, targetID)

    // 1. 查缓存
    if val, err := s.rdb.Get(ctx, key).Result(); err == nil {
        return val == "1", nil // "1"=已赞 "0"=未赞
    }

    // 2. 查 DB
    liked, err := s.repo.Exists(ctx, userID, targetType, targetID)
    if err != nil {
        return false, err
    }

    // 3. 写缓存（短 TTL，5分钟）
    if liked {
        s.rdb.Set(ctx, key, "1", 5*time.Minute)
    } else {
        s.rdb.Set(ctx, key, "0", 5*time.Minute)
    }
    return liked, nil
}

// 点赞/取消时删缓存
func (s *LikeService) Toggle(ctx context.Context, userID uint, targetType string, targetID uint) (bool, error) {
    liked, err := s.repo.Toggle(ctx, userID, targetType, targetID)
    if err != nil {
        return false, err
    }
    // 删缓存，下次 IsLiked 回源
    key := fmt.Sprintf("liked:%d:%s:%d", userID, targetType, targetID)
    s.rdb.Del(ctx, key)
    return liked, nil
}
```

#### 数据一致性

- Toggle 后立即删缓存，下次 IsLiked 回源 DB 拿最新状态
- 短 TTL（5分钟）兜底：即使删缓存失败，最多 5 分钟不一致
- 点赞状态不是关键数据，短暂不一致可接受

#### 关键点

- **短 TTL**：点赞状态变更频繁，TTL 不宜太长
- **Toggle 后删缓存**：保证状态变更后立即生效
- **缓存布尔值**：用 "1"/"0" 而非对象，节省内存

### 情景六：分布式锁（SET NX）

#### 业务背景

某些操作不能并发执行（如防止重复创建、库存扣减）。单机用 `sync.Mutex`，多实例部署时需要分布式锁。

#### 业务需求

- 多实例下互斥访问共享资源
- 锁有超时（防死锁）
- 锁能正确释放（防误删别人的锁）

#### 缓存方案：Redis SET NX + 唯一标识 + Lua 删锁

```go
type DistributedLock struct {
    rdb    *redis.Client
    key    string
    value  string // 唯一标识，防止误删别人的锁
}

func NewLock(rdb *redis.Client, key string, ttl time.Duration) (*DistributedLock, error) {
    value := uuid.NewString() // 唯一标识
    // SET key value NX PX ttl：不存在才设置 + 过期时间
    ok, err := rdb.SetNX(ctx, key, value, ttl).Result()
    if err != nil || !ok {
        return nil, ErrLockNotAcquired // 获取锁失败
    }
    return &DistributedLock{rdb: rdb, key: key, value: value}, nil
}

// 释放锁：必须用 Lua 脚本保证"判断+删除"原子
func (l *DistributedLock) Unlock(ctx context.Context) error {
    // Lua 脚本：只有 value 匹配才删（防止删别人的锁）
    script := `
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
    else
        return 0
    end
    `
    _, err := l.rdb.Eval(ctx, script, []string{l.key}, l.value).Result()
    return err
}

// 使用示例：防止重复创建文章
func (s *ArticleService) Create(ctx context.Context, authorID uint, input CreateArticleInput) (*model.Article, error) {
    lockKey := fmt.Sprintf("lock:create_article:%d", authorID)
    lock, err := NewLock(s.rdb, lockKey, 10*time.Second)
    if err != nil {
        return nil, ErrConcurrentCreate // 防重复提交
    }
    defer lock.Unlock(ctx)

    // ... 正常创建文章 ...
}
```

#### 为什么删锁要用 Lua

```
不用 Lua（有竞态）：
  线程A：GET key → value匹配 → 准备DEL
  ----此时锁过期，线程B获取了新锁----
  线程A：DEL key → 删掉了线程B的锁！
  线程C：获取锁成功 → A和C同时持有锁

用 Lua（原子）：
  GET + 判断 + DEL 在一个 Lua 脚本里，Redis 保证原子
```

#### 关键点

- **SET NX PX**：不存在才设置 + 过期时间，一条命令原子
- **唯一 value**：防止误删别人的锁
- **Lua 删锁**：GET + 判断 + DEL 原子执行
- **TTL 防死锁**：持有者宕机时锁自动过期

### 情景七：登录会话管理（Write-Through + TTL）

#### 业务背景

JWT 是无状态的，token 签发后在 exp 前无法撤销。需要引入有状态会话管理（见 登录管控设计.md）。Redis 天然适合存会话——带 TTL 自动过期。

#### 业务需求

- 主动登出：删 Redis 里的 session
- 改密码后旧 token 失效
- 会话自动过期（不用手动清理）

#### 缓存方案：Write-Through + TTL

```go
// 登录：创建会话（同时写缓存，不写 DB 表）
func (s *UserService) Login(ctx context.Context, input LoginInput) (string, error) {
    // ... 校验账号密码 ...
    sessionID := uuid.NewString()
    token, _ := s.jwt.GenerateToken(user.ID, user.Username, user.Role, sessionID)

    // 会话信息写 Redis（带 TTL = token 有效期）
    session := Session{
        UserID:  user.ID,
        Device:  input.Device,
        IP:      input.IP,
        LoginAt: time.Now(),
    }
    data, _ := json.Marshal(session)
    s.rdb.Set(ctx, "session:"+sessionID, data, 7*24*time.Hour)

    // 记录用户的所有会话（便于踢人/设备列表）
    s.rdb.SAdd(ctx, fmt.Sprintf("user:%d:sessions", user.ID), sessionID)
    return token, nil
}

// 鉴权中间件：校验 session 是否存在
func Auth(rdb *redis.Client, j *jwt.JWT) gin.HandlerFunc {
    return func(c *gin.Context) {
        // ... 解析 token ...
        sessionID := claims.SessionID

        // 查 session 是否还存在（被删=已登出/被踢）
        if _, err := rdb.Get(ctx, "session:"+sessionID).Result(); err == redis.Nil {
            response.Error(c, errcode.ErrSessionInvalid)
            c.Abort()
            return
        }
        c.Next()
    }
}

// 登出：删 session
func (s *UserService) Logout(ctx context.Context, sessionID string, userID uint) {
    s.rdb.Del(ctx, "session:"+sessionID)
    s.rdb.SRem(ctx, fmt.Sprintf("user:%d:sessions", userID), sessionID)
}

// 踢人：删该用户所有 session
func (s *UserService) KickUser(ctx context.Context, userID uint) {
    sessionIDs, _ := s.rdb.SMembers(ctx, fmt.Sprintf("user:%d:sessions", userID)).Result()
    pipe := s.rdb.Pipeline()
    for _, sid := range sessionIDs {
        pipe.Del(ctx, "session:"+sid)
    }
    pipe.Del(ctx, fmt.Sprintf("user:%d:sessions", userID))
    pipe.Exec(ctx)
}
```

#### 数据一致性

- Write-Through：会话只存 Redis 不存 DB，Redis 即真相
- TTL 自动过期：token 过期 = session 过期，不用手动清理
- 登出/踢人 = 删 Redis，立即生效

#### 关键点

- **Redis 即数据源**：不回源 DB，Redis 没有就是没有
- **TTL 自动过期**：不用清理过期会话
- **Set 管理用户会话列表**：支持批量踢人
- **配合 token 版本号**：改密码时 version++，旧 token 的 version 对不上即失效

## 三、数据一致性专题

缓存和 DB 是两份数据，如何保证一致是缓存设计最核心的问题。

### 四种更新策略对比

#### 策略 1：先更新 DB，再删缓存（推荐）

```go
db.Update(article)       // 1. 更新 DB
rdb.Del(cacheKey)        // 2. 删缓存
```

- **优点**：简单，删缓存失败概率低
- **风险**：删缓存失败 → 缓存还是旧值 → 不一致直到 TTL 过期
- **兜底**：TTL 到期自动失效
- **适用**：大多数场景（项目推荐用这个）

#### 策略 2：先删缓存，再更新 DB（有坑）

```go
rdb.Del(cacheKey)        // 1. 删缓存
db.Update(article)       // 2. 更新 DB
```

- **风险**：删缓存后、更新 DB 前，另一个请求读缓存未命中 → 查 DB 拿到旧值 → 写回缓存 → 缓存被旧值污染
- **不推荐**：并发下容易脏缓存

```
线程A：DEL缓存 → 准备更新DB
线程B：读缓存未命中 → 查DB(旧值) → 写缓存(旧值)
线程A：更新DB(新值)
结果：DB是新值，缓存是旧值 → 不一致
```

#### 策略 3：延迟双删（解决策略2的坑）

```go
rdb.Del(cacheKey)              // 1. 先删缓存
db.Update(article)             // 2. 更新 DB
time.Sleep(500 * time.Millisecond) // 3. 等一会儿（等并发读完成）
rdb.Del(cacheKey)              // 4. 再删一次缓存
```

- **原理**：第二次删清理掉并发读写入的旧值
- **难点**：延迟时间不好定（太短没用，太长影响性能）
- **适用**：对一致性要求较高的场景

#### 策略 4：最终一致（消息队列 / Binlog 监听）

```go
// 更新 DB 后发消息
db.Update(article)
mq.Publish("cache_invalidate", cacheKey) // 异步消息

// 消费者收到消息后删缓存
func Consume(msg) {
    rdb.Del(msg.Key)
}
```

或用 Canal 监听 DB binlog，自动删缓存：

```
DB binlog → Canal → 消息队列 → 消费者 → 删 Redis 缓存
```

- **优点**：应用代码不关心缓存失效，DB 变更自动同步
- **适用**：大型系统、缓存 key 分散、一致性要求高

### 选型建议

| 策略 | 一致性 | 复杂度 | 适用 |
|------|:------:|:------:|------|
| 先更新DB再删缓存 | 最终 | ★ | 大多数场景 ✅ |
| 先删缓存再更新DB | 差 | ★ | 不推荐 |
| 延迟双删 | 较高 | ★★ | 一致性要求高 |
| 消息队列/Binlog | 高 | ★★★ | 大型系统 |

**项目建议用"先更新 DB 再删缓存" + TTL 兜底**，简单够用。

## 四、缓存三剑客专题

### 问题 1：缓存穿透（查不存在的数据）

#### 故障场景

```
攻击者请求 article:id=999999（不存在）
缓存没有 → 查 DB → DB 也没有 → 不写缓存
每次请求都打到 DB → 用大量不存在 ID 请求 → DB 被打爆
```

#### 解决方案 A：缓存空值

```go
func GetArticle(ctx, id uint) (*Article, error) {
    key := fmt.Sprintf("article:%d", id)

    if cached, _ := rdb.Get(ctx, key).Result(); err == nil {
        if cached == "NULL" {
            return nil, ErrNotFound // 缓存的空值
        }
        return decode(cached), nil
    }

    article, _ := repo.FindByID(ctx, id)
    if article == nil {
        // 缓存空值，短 TTL（避免空值占内存太久）
        rdb.Set(ctx, key, "NULL", 1*time.Minute)
        return nil, ErrNotFound
    }
    rdb.Set(ctx, key, encode(article), 10*time.Minute)
    return article, nil
}
```

- **优点**：简单
- **缺点**：空值占内存；短 TTL 可能被频繁回源

#### 解决方案 B：布隆过滤器

```go
// 启动时加载所有文章 ID 到布隆过滤器
func InitBloomFilter() {
    ids := repo.GetAllArticleIDs()
    for _, id := range ids {
        bloomFilter.Add(id)
    }
}

func GetArticle(ctx, id uint) (*Article, error) {
    // 布隆过滤器先判断
    if !bloomFilter.MightContain(id) {
        return nil, ErrNotFound // 一定不存在，直接拒绝
    }
    // 可能存在，走正常缓存逻辑
    ...
}
```

- **原理**：布隆过滤器说"不存在"则一定不存在，说"存在"则可能存在
- **优点**：内存极小（1亿 ID 约 100MB），查询 O(1)
- **缺点**：有误判率（说存在但实际不存在）；不能删除元素

#### 对比

| 方案 | 内存 | 精确度 | 复杂度 |
|------|------|--------|--------|
| 缓存空值 | 大（每个空值一条） | 精确 | ★ |
| 布隆过滤器 | 极小 | 有误判 | ★★ |

### 问题 2：缓存击穿（热点 key 过期）

#### 故障场景

```
article:100 的缓存刚好过期
瞬间 1000 个请求同时查缓存 → 都未命中 → 都去查 DB
DB 瞬间承压 1000 倍 → 可能挂掉
```

#### 解决方案 A：互斥锁（singleflight）

```go
import "golang.org/x/sync/singleflight"

var sf singleflight.Group

func GetArticle(ctx, id uint) (*Article, error) {
    key := fmt.Sprintf("article:%d", id)

    // 1. 查缓存
    if cached, _ := rdb.Get(ctx, key).Bytes(); err == nil {
        return decode(cached), nil
    }

    // 2. singleflight：同一 key 只有一个请求查 DB，其他等待
    article, err, _ := sf.Do(key, func() (interface{}, error) {
        // 只有第一个请求执行这里
        a, err := repo.FindByID(ctx, id)
        if err != nil {
            return nil, err
        }
        // 写缓存
        rdb.Set(ctx, key, encode(a), 10*time.Minute)
        return a, nil
    })
    // 其他请求直接拿到第一个请求的结果
    return article.(*Article), err
}
```

- **原理**：同一 key 的并发请求，只让一个查 DB，其他等结果
- **优点**：Go 标准库支持，无需 Redis 分布式锁
- **缺点**：单机有效（多实例需 Redis 分布式锁）

#### 解决方案 B：热点 key 永不过期 + 逻辑过期

```go
type CacheItem struct {
    Data      interface{}
    ExpireAt   time.Time
}

func GetArticle(ctx, id uint) (*Article, error) {
    item := getFromRedis(key) // 不设 Redis TTL，永不过期

    if time.Now().Before(item.ExpireAt) {
        return item.Data, nil // 未逻辑过期，直接返回
    }

    // 逻辑过期：异步刷新，当前返回旧值
    go refreshCache(id) // 异步更新
    return item.Data, nil // 先返回旧值，不阻塞用户
}
```

- **原理**：Redis 层永不过期，数据里带逻辑过期时间；过期后异步刷新
- **优点**：用户永不等待 DB
- **缺点**：会短暂返回旧值；实现复杂

#### 对比

| 方案 | 一致性 | 复杂度 | 多实例 |
|------|:------:|:------:|:------:|
| singleflight | 高 | ★ | 单机 |
| 分布式锁 | 高 | ★★ | ✅ |
| 逻辑过期 | 低（短暂旧值） | ★★★ | ✅ |

### 问题 3：缓存雪崩（大量 key 同时过期）

#### 故障场景

```
1000 个文章缓存同时设了 10 分钟 TTL
10 分钟后全部过期 → 瞬间 1000 个请求回源 DB
DB 瞬间承压 1000 倍 → 可能挂掉
```

和击穿的区别：击穿是**一个**热点 key 过期，雪崩是**大量** key 同时过期。

#### 解决方案 A：TTL 加随机抖动

```go
// 基础 TTL + 随机偏移，让过期时间分散
ttl := 10*time.Minute + time.Duration(rand.Intn(120))*time.Second
rdb.Set(ctx, key, data, ttl) // 10~12 分钟随机过期
```

- **原理**：每个 key 的 TTL 不同，不会同时过期
- **优点**：极简，一行代码
- **缺点**：只是降低概率，不能完全避免

#### 解决方案 B：多级缓存

```go
// 本地缓存（L1）+ Redis（L2）+ DB（L3）
func GetArticle(ctx, id uint) (*Article, error) {
    // L1: 本地内存缓存（纳秒级）
    if cached := localCache.Get(key); cached != nil {
        return cached, nil
    }

    // L2: Redis 缓存（亚毫秒级）
    if cached, _ := rdb.Get(ctx, key).Bytes(); err == nil {
        localCache.Set(key, cached, 1*time.Minute) // 回填 L1
        return decode(cached), nil
    }

    // L3: DB
    article := repo.FindByID(ctx, id)
    rdb.Set(ctx, key, encode(article), 10*time.Minute) // 回填 L2
    localCache.Set(key, article, 1*time.Minute)        // 回填 L1
    return article, nil
}
```

- **原理**：Redis 挂了还有本地缓存兜底
- **优点**：抗雪崩 + 抗 Redis 故障
- **缺点**：本地缓存和 Redis 数据一致性难保证；多实例本地缓存不同步

#### 解决方案 C：熔断降级

```go
func GetArticle(ctx, id uint) (*Article, error) {
    cached, err := rdb.Get(ctx, key).Bytes()
    if err == nil {
        return decode(cached), nil
    }

    // Redis 故障时降级：查 DB，但限流保护
    if cb.Allow() { // 熔断器：DB 压力大时跳过
        article := repo.FindByID(ctx, id)
        return article, nil
    }

    // DB 也要扛不住了 → 返回降级数据（默认值/静态页）
    return getDefaultArticle(), nil
}
```

- **原理**：Redis 故障时降级到 DB，但用熔断器保护 DB 不被打爆
- **适用**：Redis 集群宕机的极端场景

#### 三种方案对比

| 方案 | 防 TTL 集中过期 | 防 Redis 宕机 | 复杂度 |
|------|:-------------:|:------------:|:------:|
| TTL 随机抖动 | ✅ | ❌ | ★ |
| 多级缓存 | ✅ | ✅ | ★★★ |
| 熔断降级 | ❌ | ✅ | ★★ |

## 五、缓存策略速查矩阵

| 场景 | 模式 | Key | TTL | 失效策略 | 一致性 |
|------|------|-----|-----|---------|:------:|
| 文章详情 | Cache-Aside | `article:public:{id}` | 10min+随机 | 更新时删 | 最终 |
| 浏览量 | Write-Behind | `view_count:{id}` | 无 | 定时回写 | 弱 |
| 排行榜 | ZSET | `trending:articles` | 无 | 自动维护 | 弱 |
| 标签列表 | Cache-Aside | `tags:all` | 1hour | 创建时删 | 最终 |
| 点赞状态 | Cache-Aside | `liked:{uid}:{type}:{tid}` | 5min | Toggle时删 | 最终 |
| 分布式锁 | SET NX | `lock:{name}` | 10s | 主动释放 | — |
| 登录会话 | Write-Through | `session:{sid}` | 7day | 登出/踢人删 | 强 |

## 七、项目改造建议

| 优先级 | 改造项 | 模式 | 收益 |
|:------:|--------|------|------|
| 🔴 | 文章详情缓存 | Cache-Aside | 最高频读接口，DB 降 90% |
| 🔴 | 浏览量改 Write-Behind | Write-Behind | 消除每次访问的 DB 写 |

| 🟢 | 点赞状态缓存 | Cache-Aside | 减少 Exists 查询 |
| 🟢 | 登录会话管理 | Write-Through | 支持 token 主动失效 |

**文章详情缓存 + 浏览量 Write-Behind** 是最该先做的两个——一个解决读压力，一个解决写压力，做完 DB 负载降一个数量级。
