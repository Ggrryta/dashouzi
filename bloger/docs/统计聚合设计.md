# 统计聚合设计专题文档

> 统计聚合是后端高频场景：排行榜、数据看板、报表统计都离不开它。
> 本文档以 **7 个情景** 为主线，每个情景给出"差方案"和"好方案"对比，讲清为什么差、为什么好。
>
> 核心法则：**聚合能一次 SQL 搞定的，绝不用循环查；能预计算的，绝不实时算。**

---

## 一、统计聚合的本质

**统计聚合 = 把分散的多行数据，通过 JOIN + GROUP BY + 聚合函数（COUNT/SUM/AVG），汇总成统计结果。**

和普通查询的区别：普通查询是"找几条记录"，聚合是"算汇总值"。

### 聚合的三大性能杀手

| 杀手 | 表现 | 后果 |
|------|------|------|
| N+1 查询 | 循环里查 DB | 100 个用户 = 101 次查询 |
| 笛卡尔积 | 多表 JOIN 不去重 | COUNT 结果膨胀 N 倍 |
| 全表扫描 | 大表实时聚合 | 百万行扫一次几秒 |

本文的 7 个情景都在解决这三个问题。

### 情景一：用户贡献榜（多表 JOIN 聚合）

#### 业务背景

博客系统需要一个"用户贡献榜"：统计每个用户的已发布文章数和未删除评论数，按文章数排序。项目已有此实现（`repository/search.go` 的 UserRanking）。

#### 业务需求

- 每个用户的文章数 + 评论数
- 没发文章没评论的用户也要显示（count=0）
- 按文章数降序，评论数次之

#### ❌ 差方案：N+1 循环查询

```go
func UserRanking_NPlus1() []UserRank {
    users := db.Find(&users)  // 1 次查询：查所有用户

    for _, u := range users {
        // 每个用户查 2 次：文章数 + 评论数
        db.Model(&Article{}).Where("author_id=? AND status='published'", u.ID).Count(&u.ArticleCount)
        db.Model(&Comment{}).Where("user_id=? AND is_deleted=false", u.ID).Count(&u.CommentCount)
    }
    // 100 个用户 = 1 + 100×2 = 201 次查询！
}
```

**问题**：
- 100 个用户 = 201 次 DB 查询，网络往返爆炸
- 每次查询都要走索引查找 + 返回，延迟累加
- 用户量越大越慢，不可扩展

#### ✅ 好方案：一条 SQL 多表 JOIN 聚合

```go
func UserRanking() []UserRank {
    db.Raw(`
        SELECT u.id, u.username,
            COUNT(DISTINCT a.id) as article_count,
            COUNT(DISTINCT c.id) as comment_count
        FROM users u
        LEFT JOIN articles a ON a.author_id = u.id AND a.status = 'published'
        LEFT JOIN comments c ON c.user_id = u.id AND c.is_deleted = false
        GROUP BY u.id, u.username
        ORDER BY article_count DESC, comment_count DESC
        LIMIT ?
    `, limit).Scan(&ranks)
    // 1 次查询搞定
}
```

**为什么好**：
- 1 次查询替代 201 次
- LEFT JOIN 保留零贡献用户
- COUNT(DISTINCT) 消除笛卡尔积重复
- 条件放 ON 不放 WHERE（防止 LEFT JOIN 退化成 INNER JOIN）

#### 笛卡尔积陷阱详解

用户 A 有 3 篇文章、5 条评论，两个 JOIN 叠加后是 3×5=15 行：

```
不加 DISTINCT：
  COUNT(a.id) = 15  ❌（实际3篇）
  COUNT(c.id) = 15  ❌（实际5条）

加 DISTINCT：
  COUNT(DISTINCT a.id) = 3  ✅
  COUNT(DISTINCT c.id) = 5  ✅
```

#### 关键点

- **多表 JOIN 聚合必须 COUNT(DISTINCT)**，否则笛卡尔积导致重复计数
- **LEFT JOIN 的过滤条件放 ON**，放 WHERE 会导致无匹配用户被过滤掉
- **一条 SQL 替代循环**，是反 N+1 的核心

### 情景二：文章列表 + 每篇评论数（N+1 问题）

#### 业务背景

文章列表页，每篇文章要显示"评论数"。不能只查文章，还要带评论数。

#### 业务需求

- 分页查 10 篇文章
- 每篇显示评论数
- 不能为每篇文章单独查一次评论数

#### ❌ 差方案：先查文章，循环查评论数

```go
func ArticleListWithCommentCount() []*Article {
    articles := db.Where("status='published'").Limit(10).Find(&articles)
    // 1 次查询

    for _, a := range articles {
        db.Model(&Comment{}).Where("article_id=? AND is_deleted=false", a.ID).Count(&a.CommentCount)
    }
    // 10 次查询
    // 总计：1 + 10 = 11 次
}
```

**问题**：10 篇文章 = 11 次查询。如果列表 50 条 = 51 次。

#### ✅ 好方案 1：JOIN + GROUP BY

```sql
SELECT a.*, COUNT(c.id) as comment_count
FROM articles a
LEFT JOIN comments c ON c.article_id = a.id AND c.is_deleted = false
WHERE a.status = 'published'
GROUP BY a.id
ORDER BY a.created_at DESC
LIMIT 10
```

一条 SQL 搞定。但注意：这里 JOIN 只有一张 comments 表，不会产生笛卡尔积（不像情景一两个 JOIN 叠加），所以 `COUNT(c.id)` 不需要 DISTINCT。

#### ✅ 好方案 2：子查询

```sql
SELECT a.*,
    (SELECT COUNT(*) FROM comments c
     WHERE c.article_id = a.id AND c.is_deleted = false) as comment_count
FROM articles a
WHERE a.status = 'published'
ORDER BY a.created_at DESC
LIMIT 10
```

子查询对每篇文章算评论数。好处是 GROUP BY 只在子查询里，外层不用聚合，分页更干净。

#### ✅ 好方案 3：冗余字段（最佳）

```sql
-- articles 表加 comment_count 字段
ALTER TABLE articles ADD COLUMN comment_count int DEFAULT 0;

-- 评论增删时同步更新
-- 创建评论时
UPDATE articles SET comment_count = comment_count + 1 WHERE id = ?;
-- 删除评论时
UPDATE articles SET comment_count = comment_count - 1 WHERE id = ?;
```

查列表时直接读字段，不用 JOIN 不用子查询。代价是增删评论时要维护计数。

#### 三种好方案对比

| 方案 | 查询次数 | 复杂度 | 适用 |
|------|:-------:|:------:|------|
| JOIN + GROUP BY | 1 | 中 | 评论数实时性要求高 |
| 子查询 | 1 | 低 | 文章数少、评论数少 |
| 冗余字段 | 0（直接读） | 低 | 读多写少、能接受维护成本 |

#### 关键点

- **N+1 是最常见的性能杀手**：列表 + 每条带统计 = 循环查 DB
- **一条 SQL 替代循环**，用 JOIN 或子查询
- **读多写少时用冗余字段**，空间换时间

### 情景三：全站文章总数（COUNT 性能）

#### 业务背景

后台首页显示"全站已发布文章总数"。看似简单，数据量大时有坑。

#### 业务需求

- 查 articles 表 status='published' 的总行数
- 结果展示在 Dashboard

#### ❌ 差方案：实时 COUNT

```sql
SELECT COUNT(*) FROM articles WHERE status = 'published';
```

**问题**：
- PG 的 `COUNT(*)` 要**扫描所有匹配行**才能数出来（不像 MySQL InnoDB 也有这个问题）
- 100 万行文章，每次 COUNT 要扫 100 万行，耗时数秒
- Dashboard 每次刷新都查，DB 压力大

#### ✅ 好方案 1：估算计数（不要求精确）

```sql
-- PG 用 pg_class.reltuples 快速估算
SELECT reltuples::bigint AS estimate
FROM pg_class WHERE relname = 'articles';
-- 精度约 95%，但耗时 < 1ms
```

Dashboard 不需要精确到个位数，估算够用。

#### ✅ 好方案 2：缓存计数

```go
func TotalArticleCount() int64 {
    // 先查缓存
    if count, err := redis.Get(ctx, "stats:article_count").Int(); err == nil {
        return int64(count)
    }
    // 缓存没有，查 DB
    var count int64
    db.Model(&Article{}).Where("status='published'").Count(&count)
    // 写缓存，5分钟过期
    redis.Set(ctx, "stats:article_count", count, 5*time.Minute)
    return count
}
```

文章创建/删除时可以主动更新缓存，或接受 5 分钟延迟。

#### ✅ 好方案 3：统计表（精确 + 快）

```sql
-- 独立统计表
CREATE TABLE stats (name varchar PRIMARY KEY, value bigint);

-- 文章发布/下架时维护
INSERT INTO stats (name, value) VALUES ('published_count', 1)
ON CONFLICT (name) DO UPDATE SET value = stats.value + 1;

-- 查询：读一行，O(1)
SELECT value FROM stats WHERE name = 'published_count';
```

#### 方案对比

| 方案 | 精确度 | 耗时 | 适用 |
|------|:------:|:----:|------|
| 实时 COUNT | 精确 | 慢（扫全表） | 数据量小 |
| 估算 | ~95% | <1ms | Dashboard 不要求精确 |
| 缓存 | 精确（有延迟） | <1ms | 可接受延迟 |
| 统计表 | 精确 | <1ms | 读写都要维护 |

#### 关键点

- **大表 COUNT(*) 很慢**，PG/MySQL 都要扫匹配行
- **不要求精确时用估算**，O(1) 搞定
- **要求精确时用缓存或统计表**，别每次实时算

### 情景四：各状态文章数量（条件聚合）

#### 业务背景

后台 Dashboard 要显示一个饼图：草稿多少篇、审核中多少篇、已发布多少篇、已归档多少篇。

#### 业务需求

- 按 status 分组统计每种状态的文章数
- 一次查询返回所有状态的计数

#### ❌ 差方案：查 4 次

```go
func StatusCounts() map[string]int64 {
    result := make(map[string]int64)
    db.Model(&Article{}).Where("status='draft'").Count(&result["draft"])
    db.Model(&Article{}).Where("status='reviewing'").Count(&result["reviewing"])
    db.Model(&Article{}).Where("status='published'").Count(&result["published"])
    db.Model(&Article{}).Where("status='archived'").Count(&result["archived"])
    // 4 次查询，每次扫表
}
```

**问题**：4 次查询，每次都要扫表过滤。

#### ✅ 好方案 1：GROUP BY

```sql
SELECT status, COUNT(*) as count
FROM articles
GROUP BY status;
-- 1 次查询，扫一遍表，按状态分组
```

```go
type StatusCount struct {
    Status string
    Count  int64
}
var counts []StatusCount
db.Model(&Article{}).Select("status, count(*) as count").Group("status").Scan(&counts)
```

#### ✅ 好方案 2：条件聚合（CASE WHEN）

如果还想在同一行里带出多个维度：

```sql
SELECT
    COUNT(*) as total,
    COUNT(*) FILTER (WHERE status = 'draft') as draft_count,
    COUNT(*) FILTER (WHERE status = 'reviewing') as reviewing_count,
    COUNT(*) FILTER (WHERE status = 'published') as published_count,
    COUNT(*) FILTER (WHERE status = 'archived') as archived_count
FROM articles;
-- 1 次查询，1 行结果，所有状态计数
```

PG 的 `FILTER` 语法（MySQL 用 `CASE WHEN`）让一次扫描同时算多个条件计数。

#### 关键点

- **多状态统计用 GROUP BY 一次查**，别每个状态查一次
- **要一行返回多维度时用条件聚合**（FILTER / CASE WHEN）
- 一次扫描同时算多个条件，比多次查询高效

### 情景五：用户行为漏斗统计（多维度去重）

#### 业务背景

运营要看用户行为漏斗：多少用户注册了、多少发了文章、多少评论了、多少点赞了。每个维度都要去重统计。

#### 业务需求

- 注册用户数
- 发过文章的用户数（去重）
- 评论过的用户数（去重）
- 点赞过的用户数（去重）

#### ❌ 差方案：4 次 COUNT

```sql
SELECT COUNT(*) FROM users;
SELECT COUNT(DISTINCT author_id) FROM articles WHERE status='published';
SELECT COUNT(DISTINCT user_id) FROM comments WHERE is_deleted=false;
SELECT COUNT(DISTINCT user_id) FROM likes;
-- 4 次查询
```

**问题**：4 次查询，每次扫不同的表。

#### ✅ 好方案：UNION ALL + 一次聚合

```sql
SELECT
    COUNT(DISTINCT user_id) as total_users,
    COUNT(DISTINCT CASE WHEN has_article THEN user_id END) as article_users,
    COUNT(DISTINCT CASE WHEN has_comment THEN user_id END) as comment_users,
    COUNT(DISTINCT CASE WHEN has_like THEN user_id END) as like_users
FROM (
    SELECT u.id as user_id, true as has_article, false as has_comment, false as has_like
    FROM users u JOIN articles a ON a.author_id = u.id AND a.status='published'
    UNION ALL
    SELECT u.id, false, true, false
    FROM users u JOIN comments c ON c.user_id = u.id AND c.is_deleted=false
    UNION ALL
    SELECT u.id, false, false, true
    FROM users u JOIN likes l ON l.user_id = u.id
    UNION ALL
    SELECT id, false, false, false
    FROM users
) behavior;
```

一条 SQL 算出整个漏斗。虽然 SQL 复杂，但只查一次。

#### 更实用的折中方案

实际中 SQL 太复杂可维护性差，可以拆成多个简单查询 + 缓存：

```go
func UserFunnel() FunnelStats {
    // 查缓存
    if cached := redis.Get("stats:funnel"); cached != "" {
        return parse(cached)
    }
    // 缓存没有，查 4 次（可并行）
    result := FunnelStats{
        Total:    countUsers(),
        Article:  countDistinctArticleAuthors(),
        Comment:  countDistinctCommenters(),
        Like:     countDistinctLikers(),
    }
    redis.Set("stats:funnel", result, 10*time.Minute) // 缓存10分钟
    return result
}
```

#### 关键点

- **COUNT(DISTINCT) 本身就慢**（要排序去重），数据量大时是瓶颈
- 漏斗统计不要求实时，**缓存 + 定时刷新**比复杂 SQL 更实用
- 复杂 SQL 虽然一次查完，但可维护性差，要权衡

### 情景六：实时排行榜（物化视图 + 缓存）

#### 业务背景

首页展示"热门文章榜"和"用户贡献榜"，要求排序 + 分页。数据量大时实时聚合太慢。

#### 业务需求

- 热门文章：按 view_count 降序取前 10
- 用户排行：按文章数降序取前 10
- 能接受几分钟延迟，不要求实时

#### ❌ 差方案：每次请求实时聚合

```go
func Trending() []*Article {
    db.Where("status='published'").Order("view_count DESC").Limit(10).Find(&articles)
    // 每次请求都查 DB
}
```

**问题**：排行榜是高频访问接口，每次实时查 DB，压力全压在数据库上。

#### ✅ 好方案 1：Redis 缓存

```go
func Trending() []*Article {
    // 先查缓存
    if cached := redis.Get("trending:articles"); cached != "" {
        return parse(cached)
    }
    // 缓存没有，查 DB
    articles := db.Where("status='published'").
        Order("view_count DESC").Limit(10).Find(&articles)
    // 写缓存，5分钟过期
    redis.Set("trending:articles", articles, 5*time.Minute)
    return articles
}
```

简单有效，5 分钟刷新一次。排行榜不要求实时，延迟可接受。

#### ✅ 好方案 2：Redis ZSET 实时排序

```go
// 文章被浏览时，view_count 累加到 Redis ZSET
func RecordView(articleID uint) {
    redis.ZIncrBy(ctx, "trending:zset", 1, fmt.Sprintf("%d", articleID))
}

// 排行榜直接查 ZSET，不用碰 DB
func Trending() []uint {
    // ZREVRANGE 取分数最高的10个
    ids := redis.ZRevRange(ctx, "trending:zset", 0, 9)
    return ids
}
```

ZSET 天然有序，O(log N) 插入 + O(1) 取 Top N。比每次查 DB 排序快得多。

#### ✅ 好方案 3：物化视图（复杂聚合场景）

对于 UserRanking 这种多表 JOIN 聚合，缓存整条 SQL 结果还不够灵活（分页怎么办？）。用物化视图预计算：

```sql
-- 创建物化视图
CREATE MATERIALIZED VIEW user_ranking_mv AS
SELECT u.id, u.username,
    COUNT(DISTINCT a.id) as article_count,
    COUNT(DISTINCT c.id) as comment_count
FROM users u
LEFT JOIN articles a ON a.author_id = u.id AND a.status = 'published'
LEFT JOIN comments c ON c.user_id = u.id AND c.is_deleted = false
GROUP BY u.id, u.username;

-- 给物化视图建索引
CREATE INDEX idx_mv_ranking ON user_ranking_mv (article_count DESC);

-- 定时刷新（每小时）
REFRESH MATERIALIZED VIEW user_ranking_mv;

-- 查询：直接查物化视图，不用每次算
SELECT * FROM user_ranking_mv ORDER BY article_count DESC LIMIT 10 OFFSET 0;
```

物化视图把聚合结果"固化"成一张表，查询时直接读，不用每次 JOIN + GROUP BY。

#### 三种方案对比

| 方案 | 实时性 | 复杂度 | 适用 |
|------|:------:|:------:|------|
| 实时查 DB | 实时 | 低 | 数据量小 |
| Redis 缓存 | 延迟N分钟 | 低 | 简单查询 |
| Redis ZSET | 近实时 | 中 | 排行榜/计数器 |
| 物化视图 | 定时刷新 | 高 | 复杂聚合+分页 |

#### 关键点

- **排行榜不要求实时**，缓存是最简单有效的优化
- **排序类用 Redis ZSET**，天然有序，比 DB ORDER BY 快
- **复杂聚合用物化视图**，预计算 + 定时刷新，查询时直接读

### 情景七：连续签到统计（窗口函数）

#### 业务背景

统计用户连续签到天数。签到记录表 `sign_ins(user_id, sign_date)`。要找出每个用户最长连续签到多少天。

#### 业务需求

- 每个用户的最长连续签到天数
- 当前是否在连续签到中

#### ❌ 差方案：应用层循环判断

```go
func MaxConsecutiveDays(userID uint) int {
    dates := db.Where("user_id=?", userID).Order("sign_date").Pluck("sign_date")
    // 查出所有签到日期，在 Go 里遍历判断连续
    maxStreak := 0
    current := 1
    for i := 1; i < len(dates); i++ {
        if dates[i] == dates[i-1].AddDate(0, 0, 1) {
            current++
        } else {
            maxStreak = max(maxStreak, current)
            current = 1
        }
    }
    return max(maxStreak, current)
}
```

**问题**：查出全部日期到内存再算，数据量大时内存和传输开销大。

#### ✅ 好方案：SQL 窗口函数

```sql
WITH dated AS (
    SELECT user_id, sign_date,
        sign_date - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY sign_date)) * INTERVAL '1 day' as grp
    FROM sign_ins
)
SELECT user_id, MAX(streak) as max_streak
FROM (
    SELECT user_id, grp, COUNT(*) as streak
    FROM dated
    GROUP BY user_id, grp
) streaks
GROUP BY user_id;
```

**原理**：用 `ROW_NUMBER()` 给签到日期编号，`sign_date - 编号` 相同的行属于同一连续段（因为连续日期减去递增编号会得到相同的基准日期）。再按段 GROUP BY 算每段天数，取最大值。

一次 SQL 搞定，不用把数据拉到内存。

#### 关键点

- **窗口函数（OVER / PARTITION BY / ROW_NUMBER）是处理"连续""排名"类问题的利器**
- 能在 SQL 层完成的计算，不要拉到应用层循环
- 窗口函数面试高频，尤其互联网大厂

## 三、差方案 vs 好方案总结

| 情景 | 差方案 | 问题 | 好方案 | 收益 |
|------|--------|------|--------|------|
| 用户贡献榜 | N+1 循环查 | 201次查询 | 多表JOIN聚合 | 1次查询 |
| 列表+计数 | 循环查评论数 | 11次查询 | JOIN/子查询/冗余字段 | 1次或0次 |
| 文章总数 | 实时COUNT | 扫全表 | 估算/缓存/统计表 | O(1) |
| 状态分布 | 查4次 | 4次扫表 | GROUP BY / 条件聚合 | 1次扫表 |
| 漏斗统计 | 4次COUNT | 4次去重 | UNION ALL / 缓存 | 1次或缓存 |
| 排行榜 | 实时聚合 | 高频查DB | Redis缓存/ZSET/物化视图 | 不碰DB |
| 连续签到 | 内存循环 | 全量拉取 | 窗口函数 | SQL层完成 |

## 四、性能优化层级

统计聚合的优化从低到高分五层，按需选择：

```
第1层：一条 SQL 替代 N+1 循环       ← 消除多余查询（情景一、二）
第2层：GROUP BY + 条件聚合           ← 一次扫描算多维度（情景四）
第3层：COUNT 估算 / 统计表           ← 避免大表 COUNT（情景三）
第4层：Redis 缓存 / ZSET             ← 不碰 DB（情景六）
第5层：物化视图 / 离线预计算          ← 复杂聚合预计算（情景六）
```

**能不做聚合就不做（冗余字段），必须做就一次搞定（一条SQL），做完了就缓存（Redis/物化视图）。**

## 五、常用 SQL 技巧速查

| 技巧 | 语法 | 解决什么 |
|------|------|---------|
| LEFT JOIN | `LEFT JOIN ... ON ...` | 保留零记录的行 |
| COUNT(DISTINCT) | `COUNT(DISTINCT col)` | 笛卡尔积去重 |
| 条件放 ON | `LEFT JOIN ... ON cond AND filter` | LEFT JOIN 不退化 |
| 条件聚合 | `COUNT(*) FILTER (WHERE ...)` | 一次扫描算多维度 |
| 子查询计数 | `(SELECT COUNT(*) FROM ...)` | 避免 GROUP BY 影响分页 |
| 窗口函数 | `ROW_NUMBER() OVER (PARTITION BY ...)` | 连续/排名类问题 |
| 物化视图 | `CREATE MATERIALIZED VIEW` | 预计算复杂聚合 |
| 估算计数 | `pg_class.reltuples` | 大表快速估算 |

## 六、本项目统计模块现状

| 接口 | 当前实现 | 评价 | 可优化方向 |
|------|---------|:----:|-----------|
| UserRanking | 多表JOIN + COUNT DISTINCT | ✅ 好 | 加物化视图/缓存 |
| Trending | ORDER BY view_count | ✅ 够用 | 加 Redis 缓存 |
| 文章总数 | 无 | — | 加统计表或缓存 |
| 状态分布 | 无 | — | 加 GROUP BY 查询 |
| 浏览量 | 同步 UPDATE | ⚠️ | 改 Redis 累计 + 批量回写 |

项目统计聚合的 SQL 写得正确（UserRanking 的三个技术点都对），但缺少缓存和预计算层——数据量大了之后，实时聚合会成为瓶颈。这是模块 9 review 后该补的方向。
