# 业务方法审查清单

> 写完一个业务方法，主动过一遍这张表，能提前堵住大部分生产事故。
> 本清单是 `REVIEW-GUIDE.md` 的方法级补充：REVIEW-GUIDE 按"模块"审查，本清单按"方法"审查。
>
> 审查标尺不是"能不能跑"，而是"生产级够不够"——功能跑通 ≠ 生产级，差的就是这些维度。

---

## 一、为什么需要这张清单

写业务方法时，开发者容易陷入"把 happy path 写通就提交"的惯性。但一个生产级业务方法，除了"逻辑正确"，还要经得起：并发请求、重复提交、部分失败、越权访问、故障排查、性能压力。

并发和幂等只是其中两个维度。完整的视角应该覆盖 **正确性、健壮性、安全、可运维、性能** 五大类，共 17 个检查项。

---

## 二、五大类维度详解

### 类一：正确性（业务逻辑对不对）

#### 1. 事务一致性

多个写操作必须原子。一个方法里如果有多个 INSERT/UPDATE/DELETE，要么全成功要么全回滚。

- **检查问题**：这个方法里所有写操作，在同一个事务里吗？部分失败会回滚吗？
- **反例**：先建标签、再建文章，没包事务 → 文章创建失败时产生孤儿标签。
- **正解**：`db.Transaction(func(tx) error { ... })` 包裹全部写操作。

#### 2. 校验完整性

入参的每个字段都应有约束，不能只校验一部分。

- **检查问题**：每个字段都校验了吗？边界值（空、超长、负数、0、nil）处理了吗？
- **反例**：只校验 `title` 非空，但 `content` 没校验、长度没限制、`TagNames` 数量没上限。
- **正解**：明确每个字段的约束（非空/长度/范围/格式），在 service 入口统一校验。

#### 3. 数据一致性

改了 A 是否要同步改 B？派生数据是否需要更新？

- **检查问题**：这次写入会让哪些派生数据/缓存/计数器失效？都同步了吗？
- **反例**：创建文章后没更新作者的 `article_count`，导致统计不准。
- **正解**：识别所有派生数据，在同一事务内或通过事件机制同步更新。

#### 4. 状态合法性

涉及状态字段的，必须经过状态机校验，不能直接赋值。

- **检查问题**：写入的状态是合法的吗？经过流转校验了吗？
- **正例**：用 `map[状态]map[目标]bool` 配置表校验流转，非法跳转直接拒绝。
- **反例**：直接 `article.Status = "published"`，绕过校验。

---

### 类二：健壮性（出错时怎么办）

#### 5. 错误分类与可恢复性

错误要能区分"业务可恢复"（重试有用）和"系统不可恢复"（重试没用）。

- **检查问题**：错误能区分"可恢复"和"不可恢复"吗？调用方知道该重试还是该报错吗？
- **反例**：所有 error 一股脑返回，调用方无法区分"slug 冲突"（换一个重试）和"DB 挂了"（重试也没用）。
- **正解**：定义清晰的领域错误（`ErrDuplicate`/`ErrNotFound`/`ErrInternal`），handler 层映射到不同 HTTP 状态码。

#### 6. 边界条件

空集合、nil、极值、超长输入，每个分支都要覆盖。

- **检查问题**：空值/nil/空数组/极值/超长，都测过了吗？
- **检查清单**：
  - 切片为 nil vs 空切片 `[]`
  - 字符串为空 vs 只有空格
  - 数值为 0、负数、最大值
  - 输入超长（10MB content、1000 个标签）

#### 7. 资源管理

context 超时/取消要能传递下去，连接/文件句柄要释放。

- **检查问题**：ctx 取消时能及时中断吗？有没有资源泄漏？
- **正解**：所有 DB 调用都传 `ctx`，用 `defer` 释放资源，设置合理的超时。

---

### 类三：安全（会不会被攻击/越权）

#### 8. 权限（纵深防御）

不能全靠上层中间件，service 层也应校验权限。

- **检查问题**：service 层自己校验了权限吗，还是全指望上层中间件？
- **反例**：service 层完全不校验角色，一旦被内部 RPC 直接调用，reader 也能创建文章。
- **正解**：service 层对敏感操作二次校验角色/所有权，形成纵深防御。

#### 9. 越权（IDOR）

通过传入的 ID 能否访问到不该看的资源。

- **检查问题**：通过 ID 访问的资源，做了所有权/可见性校验吗？
- **正例**：`if !isAdmin(role) && article.AuthorID != userID { return ErrNotOwner }`。
- **反例**：直接按 ID 查询返回，不校验是否属于当前用户。

#### 10. 注入

所有用户输入必须参数化，不能字符串拼接 SQL。

- **检查问题**：所有用户输入都走参数化了吗？有没有字符串拼接 SQL？
- **正例**：`Where("name = ?", name)` 参数化查询。
- **反例**：`fmt.Sprintf("WHERE name = '%s'", name)` 拼接 SQL。

#### 11. 敏感数据泄露

返回值不能包含不该暴露的字段。

- **检查问题**：返回值里有没有不该暴露的字段？
- **正例**：返回 `dto.ArticleResponse`，只含白名单字段。
- **反例**：返回 `model.User`，导致 `password_hash` 泄露到 JSON。

---

### 类四：并发与幂等

#### 12. 并发安全

check-then-act 必须改成原子操作。

- **检查问题**：先查后写的操作，中间有时间窗口吗？并发下会竞态吗？
- **反例**：`FindOrCreate` 先 SELECT 再 INSERT，并发下两个请求都查到 not found，都去 INSERT。
- **正解**：靠 DB 唯一约束 + `ON CONFLICT DO NOTHING` + 回查，让 DB 做原子去重。

#### 13. 幂等性

同一请求执行一次和多次，效果相同。

- **检查问题**：重复调用效果一致吗？有幂等键吗？
- **反例**：每次生成随机 slug + 纯 INSERT，重复提交创建多条记录。
- **正解**：引入客户端幂等键（`idempotency_key`），或基于唯一约束去重。

---

### 类五：可运维性（出事了能不能查）

#### 14. 可观测性

关键操作要有日志、指标、追踪。

- **检查问题**：关键操作有日志吗？有 metric（成功率/QPS/耗时）吗？有 trace 串联吗？
- **反例**：整个方法无任何日志，生产失败无法排查。
- **正解**：结构化日志记录入参/结果/耗时，关键路径埋 metric，接入 OpenTelemetry trace。

#### 15. 审计

"谁在什么时候创建/修改了什么"——合规场景必备。

- **检查问题**：这次写操作需要审计留痕吗？谁操作的、改了什么、何时改的？
- **正解**：写审计表记录 operator_id / action / before / after / timestamp。

#### 16. 限流/降级

接口会不会被滥用？依赖故障时能否降级？

- **检查问题**：这个接口会被滥用吗？需要限流吗？依赖降级了吗？
- **正解**：写接口加速率限制，依赖故障时返回降级响应而非雪崩。

---

### 类六：性能（够不够快）

#### 17. N+1 查询

循环里不能有 DB 调用。

- **检查问题**：循环里有 DB 调用吗？能不能批量查询/批量插入？
- **反例**：`for _, name := range tags { repo.FindOrCreate(name) }`，10 个标签 = 10+ 次 DB 往返。
- **正解**：一次 `SELECT ... WHERE name IN (...)` 批量查，缺失的批量 `INSERT`。

#### 18. 索引命中

查询条件要走索引，不能全表扫描。

- **检查问题**：查询条件都走了索引吗？有没有全表扫描？
- **正例**：`Where("name = ?", name)` 命中 uniqueIndex。
- **反例**：`ILIKE '%kw%'` 前导通配符，无法走索引，全表扫描。

#### 19. 锁竞争

并发写同一行要有锁策略。

- **检查问题**：并发写同一行会冲突吗？用的乐观锁还是悲观锁？
- **反例**：read-then-write 无锁，两个请求同时改状态会错乱。
- **正解**：乐观锁 `UPDATE ... WHERE id=? AND version=?`，靠 RowsAffected 判断是否被抢；或行锁 `SELECT ... FOR UPDATE`。

## 三、自检清单（实操版）

写完一个业务方法，逐项打勾：

```
【正确性】
 □ 1. 多步写操作在同一个事务里吗？部分失败能回滚吗？
 □ 2. 每个入参字段都校验了（非空/长度/范围/格式）吗？边界值处理了吗？
 □ 3. 派生数据（计数/缓存/关联状态）都同步了吗？
 □ 4. 状态字段经过合法性校验了吗？

【健壮性】
 □ 5. 错误能区分"可恢复"和"不可恢复"吗？调用方知道该重试还是报错吗？
 □ 6. 空值/nil/空数组/极值/超长，每个分支都测过吗？
 □ 7. context 取消能及时中断吗？有资源泄漏吗？

【安全】
 □ 8. service 层自己校验了权限吗？还是全靠上层中间件？
 □ 9. 通过 ID 访问的资源做了越权校验吗？
 □ 10. 用户输入都参数化了吗？没拼 SQL 吗？
 □ 11. 返回值没有泄露敏感字段吗？

【并发与幂等】
 □ 12. check-then-act 改成原子操作了吗？并发下会竞态吗？
 □ 13. 重复调用效果一致吗？有幂等键吗？

【可运维】
 □ 14. 关键操作有日志/metric/trace 吗？
 □ 15. 需要审计的操作留痕了吗？
 □ 16. 接口需要限流吗？依赖故障能降级吗？

【性能】
 □ 17. 循环里没有 N+1 DB 调用吧？能批量化吗？
 □ 18. 查询条件命中索引了吗？有没有全表扫描？
 □ 19. 并发写同一行有锁策略吗？乐观锁还是悲观锁？
```

## 四、使用方式

1. **写代码时**：每完成一个 service 方法，过一遍自检清单，逐项确认。
2. **Code Review 时**：作为 review 的检查表，逐项审查被改动的方法。
3. **排查事故时**：对照清单定位"哪个维度没考虑到"导致的故障。
4. **面试准备时**：每个维度都能展开讲"为什么需要、怎么实现、反例是什么"。

### 与 REVIEW-GUIDE.md 的关系

| 文档 | 审查粒度 | 用途 |
|------|---------|------|
| `REVIEW-GUIDE.md` | 模块级（11 个模块） | 按模块理解整体设计、找设计差距 |
| `业务方法审查清单.md`（本文档） | 方法级（单个 service 方法） | 写/审单个方法时的逐项检查 |

两者配合：先用 REVIEW-GUIDE 按模块建立全局认知，再用本清单对每个模块里的关键方法做方法级审查。
