# 幂等设计专题文档

> 幂等不是一种技术，而是一组技术按场景选择。
> 本文档以 **7 个真实业务情景** 为主线，每个情景给出业务背景、故障场景、幂等方案与伪代码。
>
> 核心判断法则：**业务有没有天然唯一键**——有就用数据库约束，没有就靠业务引入标识。

---

## 一、幂等的本质

**幂等 = 同一请求执行一次和多次，结果相同。**

四类操作的幂等难度不同：

| 操作类型 | 天然幂等 | 原因 |
|---------|:-------:|------|
| 读取 GET | ✅ | 不改数据，调多少次都一样 |
| 删除 DELETE | ✅ | 删一次后再删，结果还是"不存在" |
| 覆盖式更新 PUT | ✅ | 设成固定值，重复设结果不变 |
| 累加式更新 | ❌ | 每次 +1，调 2 次变 +2 |
| 创建 POST | ❌ | 每次插新行，调 2 次变 2 条 |

**幂等方案主要针对"累加更新"和"创建"两类。**

### 情景一：点赞 / 收藏（有天然唯一键）

#### 业务背景

博客系统允许用户对文章点赞。一个用户对同一篇文章只能赞一次，再点一次是取消（Toggle 语义）。

#### 业务需求

- 用户 A 对文章 10 点赞 → 创建一条点赞记录
- 用户 A 再次"点赞"（网络重试 / 双击）→ 取消，不会创建第二条
- 并发场景下两个请求同时到达，不会产生重复记录

#### 不做幂等会怎样

```
用户A 点赞文章10（网络超时）
用户A 重试点赞文章10
→ likes 表出现两条 (user_id=1, article_id=10) 记录 → 数据脏
```

#### 幂等方案：唯一约束 + ON CONFLICT

点赞有天然业务唯一键：`(user_id, target_type, target_id)`。用数据库唯一约束做兜底，冲突时跳过。

#### 伪代码

```go
// model: likes 表唯一约束 (user_id, target_type, target_id)
type Like struct {
    UserID     uint   `gorm:"uniqueIndex:uk_like_target"`
    TargetType string `gorm:"uniqueIndex:uk_like_target"`
    TargetID   uint   `gorm:"uniqueIndex:uk_like_target"`
}

// repository: 事务内 ON CONFLICT + RowsAffected 判断状态
func (r *likeRepo) Toggle(ctx, userID, targetType, targetID) (liked bool, err error) {
    err = r.db.Transaction(func(tx *gorm.DB) error {
        // 先尝试删除（取消赞）
        res := tx.Where("user_id=? AND target_type=? AND target_id=?", userID, targetType, targetID).
            Delete(&model.Like{})
        if res.RowsAffected > 0 {
            liked = false  // 删掉了 = 之前赞过，现在是取消
            return nil
        }
        // 没删掉 = 之前没赞过，现在创建
        res = tx.Clauses(clause.OnConflict{
            Columns:   []clause.Column{{Name: "user_id"}, {Name: "target_type"}, {Name: "target_id"}},
            DoNothing: true,
        }).Create(&model.Like{UserID: userID, TargetType: targetType, TargetID: targetID})
        liked = res.RowsAffected > 0  // 1=新建成功, 0=并发冲突已被别人创建
        return nil
    })
    return
}
```

#### 关键点

- **三层幂等保障**：① 先删判断 ② ON CONFLICT 冲突跳过 ③ 唯一约束兜底
- 并发下两个请求同时 Create，唯一约束让第二个 RowsAffected=0，不会重复
- **这是最优雅的幂等方案**，因为业务有天然唯一键

#### 适用条件

业务存在天然唯一键：点赞（用户+目标）、收藏（用户+文章）、关注（用户+用户）

### 情景二：创建文章 / 下单（无天然唯一键）

#### 业务背景

用户在博客编辑器写完文章，点"发布"。网络抖动导致请求超时，前端自动重试，或用户手抖连点两次。

#### 业务需求

- 用户提交一次 → 创建一篇文章
- 网络重试 / 双击 → 返回第一次创建的那篇文章，**不创建第二篇**
- 允许两篇标题相同的文章（"周报"可以发多篇）

#### 不做幂等会怎样

```
用户提交文章"周报"（超时）
用户重试提交文章"周报"
→ articles 表出现两篇内容相同的"周报" → 垃圾数据
```

#### 幂等方案：幂等键（Idempotency Key）

文章没有天然唯一键（标题可重复），靠客户端为每次"创建意图"生成唯一 ID，服务端记录 key→结果。

#### 伪代码

```go
// 1. 文章表加幂等键字段（唯一约束）
type Article struct {
    ...
    IdempotencyKey string `gorm:"uniqueIndex;size:64" json:"-"`
}

// 2. handler 接收客户端传入的幂等键
type createArticleReq struct {
    Title          string `json:"title" binding:"required"`
    Content        string `json:"content" binding:"required"`
    IdempotencyKey string `json:"idempotency_key" binding:"required"` // 强制要求
}

// 3. service: 查 key → 没有则建 → 唯一约束兜底并发
func (s *ArticleService) Create(ctx, authorID, input) (*Article, error) {
    key := input.IdempotencyKey
    article := &Article{..., IdempotencyKey: key}

    err := s.runInTx(ctx, func(ar, tr) error {
        // 幂等校验：同一 key 是否已创建过
        if existing, _ := ar.FindByIdempotencyKey(ctx, key); existing != nil {
            *article = *existing  // 返回上次创建的结果
            return nil
        }
        // 没创建过 → 执行创建
        if err := ar.Create(ctx, article); err != nil {
            // 唯一约束冲突 = 并发重复，回查已有结果
            if isUniqueViolation(err) {
                existing, _ := ar.FindByIdempotencyKey(ctx, key)
                if existing != nil {
                    *article = *existing
                    return nil
                }
            }
            return err
        }
        return nil
    })
    return article, err
}
```

#### 客户端配合

```javascript
// 前端：每次提交生成唯一 key（同一次重试用同一个 key）
const key = crypto.randomUUID()
fetch('/articles', {
    method: 'POST',
    body: JSON.stringify({ title, content, idempotency_key: key })
})
// 超时重试时，用同一个 key 重发
```

#### 关键点

- **check-then-act 仍有竞态**，必须靠 `uniqueIndex` 兜底 + 冲突后回查
- key 的生命周期：可永久存（DB），或设 TTL（Redis）
- 与方案一对比：**没有天然唯一键，就得业务自己造一个**

#### 适用条件

创建型操作且无天然唯一键：发文章、下单、发消息、创建订单

### 情景三：订单支付 / 文章发布（状态流转）

#### 业务背景

用户对订单点击"支付"。支付网关回调可能重复通知（至少一次语义）。文章发布也类似：状态从 draft → published，重复"发布"请求不该出错。

#### 业务需求

- 订单从"待支付"→"已支付"，扣款一次
- 支付回调重复通知 → 不重复扣款，返回"已支付"
- 已支付的订单再次"支付" → 幂等成功，不报错

#### 不做幂等会怎样

```
支付网关回调通知①：订单100 已支付 → 扣款 99元
支付网关回调通知②（重复）：订单100 已支付 → 再扣 99元
→ 用户被扣两次钱 → 资损事故
```

#### 幂等方案：状态机前置校验

状态本身就是天然幂等键——"已经是目标状态"就不再重复操作。

#### 伪代码

```go
// 状态机：合法流转
var validTransitions = map[string]map[string]bool{
    "pending":   {"paid": true, "cancelled": true},
    "paid":      {"refunded": true},
    "refunded":  {},
    "cancelled": {},
}

func (s *OrderService) Pay(ctx, orderID) error {
    order, _ := s.repo.FindByID(ctx, orderID)

    // ← 幂等核心：已是目标状态，直接返回成功
    if order.Status == "paid" {
        return nil  // 重复回调，幂等返回
    }

    // 校验状态流转合法性
    if !validTransitions[order.Status]["paid"] {
        return ErrInvalidTransition  // cancelled/refunded 不能再支付
    }

    // 执行支付 + 状态变更（事务内）
    return s.runInTx(ctx, func(tx) error {
        if err := s.paymentGateway.Charge(order.Amount); err != nil {
            return err
        }
        order.Status = "paid"
        order.PaidAt = &now
        return s.repo.Update(ctx, order)
    })
}
```

#### 并发兜底

状态机校验是 check-then-act，并发下仍可能两个请求同时读到 `pending`。用乐观锁兜底：

```sql
-- 带状态条件的 UPDATE，保证只生效一次
UPDATE orders
SET status = 'paid', version = version + 1, paid_at = NOW()
WHERE id = 100 AND status = 'pending' AND version = 5
-- RowsAffected=0 说明已被抢或已支付，幂等返回
```

#### 关键点

- **状态即幂等键**，不需要额外字段
- "已处于目标状态"是天然的幂等返回点
- 配合乐观锁防并发竞态

#### 适用条件

有状态流转的业务：订单支付、文章发布、审批流、退款

### 情景四：库存扣减（并发更新）

#### 业务背景

秒杀场景，商品库存 10 件，100 个用户同时抢购。每个请求要扣减库存 1。

#### 业务需求

- 库存从 10 扣到 9，再扣到 8...
- 库存为 0 时拒绝下单
- 并发下不能超卖（扣成负数）
- 请求重试不能重复扣减

#### 不做幂等会怎样

```
库存=1，用户A 和 用户B 同时下单
两个请求都读到 stock=1，都判断"够"，都扣减
→ stock 变成 -1 → 超卖
```

#### 幂等方案：乐观锁（条件更新）

用带条件的 UPDATE 保证原子性，版本/状态不匹配则不执行。

#### 伪代码

```go
func (s *SkuService) DeductStock(ctx, skuID, orderKey string) error {
    // orderKey 是订单维度幂等键，防同一订单重复扣库存
    if existing := s.redis.Get(ctx, "deducted:"+orderKey); existing != "" {
        return nil  // 该订单已扣过库存
    }

    // 带库存条件的原子更新：stock > 0 才扣
    res := s.db.Model(&Sku{}).
        Where("id = ? AND stock > 0", skuID).
        UpdateColumn("stock", gorm.Expr("stock - 1"))

    if res.RowsAffected == 0 {
        return ErrOutOfStock  // 库存不足或不存在
    }

    // 标记该订单已扣库存（防重试重复扣）
    s.redis.Set(ctx, "deducted:"+orderKey, "1", 24*time.Hour)
    return nil
}
```

#### 进阶：CAS 乐观锁版本号

```sql
-- 读时拿到 version=5
UPDATE skus SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5 AND stock > 0
-- RowsAffected=0：要么被别人抢了(version变了)，要么库存为0
```

#### 关键点

- **条件 UPDATE 是原子的**，天然防超卖
- `stock > 0` 条件保证不扣成负数
- 配合订单级幂等键（Redis 标记）防同一订单重复扣
- 乐观锁双重作用：防并发覆盖 + 防重复执行

#### 适用条件

并发更新同一资源：库存扣减、余额变更、计数器

### 情景五：消息消费（MQ 重复投递）

#### 业务背景

订单服务发消息通知物流发货。MQ 保证"至少一次"投递，意味着同一条消息可能被消费多次。

#### 业务需求

- 消费消息 → 创建物流单
- 消息重复投递 → 不创建重复物流单
- 消费失败重试 → 不重复处理

#### 不做幂等会怎样

```
MQ 投递消息①：订单100 发货 → 创建物流单A
MQ 重复投递消息②：订单100 发货 → 创建物流单B
→ 一个订单两个物流单 → 重复发货
```

#### 幂等方案：去重表

独立一张表记录已处理的消息 ID，消费前先查去重表。

#### 伪代码

```go
func (s *LogisticsConsumer) Handle(msg Message) error {
    return s.db.Transaction(func(tx *gorm.DB) error {
        // 1. 先往去重表插消息ID（唯一约束兜底并发）
        res := tx.Clauses(clause.OnConflict{DoNothing: true}).
            Create(&IdempotentRecord{
                RequestID: msg.MessageID,  // MQ 消息的唯一 ID
                Action:    "create_logistics",
            })

        if res.RowsAffected == 0 {
            // 已处理过，幂等返回
            return nil
        }

        // 2. 没处理过 → 执行业务
        order, _ := s.findOrder(tx, msg.OrderID)
        if order.Status != "paid" {
            return ErrOrderNotPaid
        }

        logistics := &Logistics{OrderID: msg.OrderID, ...}
        return tx.Create(logistics).Error
    })
}
```

#### 为什么用去重表而非幂等键字段

- 物流单表不该耦合"消息处理"的逻辑
- 去重表通用，可服务多个消费场景（用 action 字段区分）
- 去重表和业务操作在**同一事务**内，保证原子

#### 关键点

- 消息 ID 作为天然幂等键（MQ 都会提供 MessageID）
- 去重表插成功 + 业务执行在同一事务内
- `ON CONFLICT DO NOTHING` 处理并发重复

#### 适用条件

消息驱动场景：MQ 消费、事件处理、回调通知

### 情景六：表单提交防双击（防重）

#### 业务背景

用户填写注册表单，点"提交"。网络慢，用户以为没点上，又点了一次。

#### 业务需求

- 第一次提交 → 正常处理
- 第二次提交（双击）→ 拒绝，提示"请勿重复提交"
- 注意：这里要的是**防重**（第二次拒绝），不是幂等（第二次返回第一次结果）

#### 不做防重会怎样

```
用户双击"注册"
请求①：创建账号 alice@example.com → 成功
请求②：创建账号 alice@example.com → 邮箱已存在，报错
→ 用户体验差（明明成功了却看到错误）
```

#### 幂等方案：防重 Token（一次性令牌）

服务端发一次性 token，用完即删，第二次提交 token 已失效。

#### 伪代码

```go
// 1. 前端进入表单页时，先请求 token
//    GET /api/form-token → 服务端生成并存 Redis
func GetFormToken(c *gin.Context) {
    token := uuid.NewString()
    redis.Set(ctx, "form_token:"+token, "1", 5*time.Minute) // 5分钟有效
    response.Success(c, token)
}

// 2. 提交表单时带上 token
//    POST /register  body: { ..., form_token: "xxx" }
func Register(c *gin.Context) {
    token := req.FormToken

    // ← 防重核心：删除 token，删成功=第一次，删失败=重复
    deleted, _ := redis.Del(ctx, "form_token:"+token).Result()
    if deleted == 0 {
        response.Error(c, errcode.ErrDuplicateSubmit) // "请勿重复提交"
        return
    }

    // 正常处理注册
    ...
}
```

#### 防重 vs 幂等 的区别

| | 防重（Token） | 幂等（Idempotency Key） |
|---|---|---|
| 第二次请求 | **拒绝**（报错） | **返回第一次的结果** |
| 客户端体验 | 看到错误提示 | 看到成功（和第一次一样） |
| 适用 | 表单防双击 | 网络重试需要拿到结果 |

#### 关键点

- Token 是**一次性**的，`Del` 操作原子，天然防并发
- 与幂等键配合：前端 Token 防双击 + 后端幂等键防重试

#### 适用条件

表单提交、按钮防双击等前端交互场景

### 情景七：浏览量统计（累加非幂等）

#### 业务背景

博客文章详情页每次访问，`view_count + 1`。高并发下同步写 DB 是瓶颈，且用户刷新页面会重复计数。

#### 业务需求

- 文章被访问 → 浏览量 +1
- 用户短时间刷新页面 → 不重复计数（防刷）
- 高并发 → 不能每次都同步写 DB

#### 不做处理会怎样

```
用户连续刷新 10 次
→ view_count + 10 → 数据虚高
→ 每次都 UPDATE articles → DB 压力大
```

#### 幂等方案：Redis 累计 + 批量回写 + 用户去重

```go
func (s *ArticleService) RecordView(ctx, articleID, userID) error {
    // 1. 用户维度去重：同一用户 5 分钟内重复访问不计数
    viewedKey := fmt.Sprintf("viewed:%d:%d", userID, articleID)
    if set, _ := redis.SetNX(ctx, viewedKey, "1", 5*time.Minute); !set {
        return nil  // 5分钟内已访问过，不重复计数
    }

    // 2. 浏览量先累加到 Redis（INCR 原子，高并发友好）
    countKey := fmt.Sprintf("view_count:%d", articleID)
    count, _ := redis.Incr(ctx, countKey).Result()

    // 3. 每累积 100 次批量回写 DB（减轻 DB 压力）
    if count % 100 == 0 {
        s.repo.BatchIncrementViewCount(ctx, articleID, 100)
        redis.Set(ctx, countKey, "0", 0) // 重置计数器
    }
    return nil
}
```

#### 关键点

- `view_count + 1` 是累加，天然**不幂等**——重复调用会多加
- 用 Redis `SetNX` 做用户级去重（防刷新）
- 用 Redis `INCR` 做原子累加 + 批量回写（减 DB 压力）
- 严格来说这不是"幂等"，而是"去重 + 异步累计"，但解决的问题相同

#### 适用条件

计数器、浏览量、排行榜等累加型统计

## 三、方案选型决策树

```
操作是读 / 删 / 覆盖更新吗？
├─ 是 → 天然幂等，无需处理
└─ 否 → 是创建操作吗？
    ├─ 是 → 有天然业务唯一键？
    │       ├─ 有 → 唯一约束 + ON CONFLICT（情景一）
    │       └─ 无 → 客户端能传幂等键？
    │               ├─ 能 → 幂等键 + 唯一约束（情景二）
    │               └─ 不能 → 去重表（情景五）
    └─ 否 → 是状态变更吗？
            ├─ 是 → 状态机前置校验 + 乐观锁（情景三）
            └─ 否 → 是并发更新吗？
                    └─ 是 → 条件 UPDATE / 乐观锁（情景四）
```

## 四、方案速查矩阵

| 方案 | 核心机制 | 适用场景 | 伪代码情景 | 难度 |
|------|---------|---------|-----------|:----:|
| 唯一约束 + ON CONFLICT | DB 唯一键兜底 | 有天然唯一键的创建 | 情景一 点赞 | ★ |
| 幂等键 | 客户端 requestId + 服务端记录 | 无唯一键的创建 | 情景二 发文章 | ★★ |
| 状态机前置 | 已是目标状态则返回 | 状态流转 | 情景三 支付 | ★★ |
| 乐观锁 | 条件 UPDATE + 版本号 | 并发更新 | 情景四 库存 | ★★ |
| 去重表 | 独立表记录已处理请求 | MQ 消费 | 情景五 消息 | ★★ |
| 防重 Token | 一次性令牌用完即删 | 表单防双击 | 情景六 注册 | ★ |
| Redis 累计 + 去重 | SetNX 去重 + INCR 累加 | 计数器统计 | 情景七 浏览量 | ★★ |

## 五、防重 vs 幂等

这两个概念经常混淆，但本质不同：

| | 防重 | 幂等 |
|---|---|---|
| 第二次请求 | **拒绝**（报错） | **返回第一次的结果** |
| 客户端体验 | 看到错误 | 看到成功 |
| 典型方案 | Token | 幂等键 |
| 适用场景 | 表单防双击 | 网络重试 |
| 配合使用 | 前端 Token 防双击 + 后端幂等键防重试 | |

**支付场景要的是幂等**（重试也要拿到支付结果，不能只报错）；**表单防双击要的是防重**（第二次就该拦住）。
