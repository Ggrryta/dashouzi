# 实时拍卖系统 - 产品需求规格（PRD）

> 本文档描述"做什么"，不描述"怎么做"。技术实现细节见 `docs/ARCHITECTURE.md`，接口契约见 `api/openapi.yaml`。

---

## 1. 项目背景与目标

### 1.1 背景

实时拍卖系统是一个高并发、强状态、低延迟的业务场景：
- 一个房间内可同时拍卖多个商品，每个商品独立计时、独立出价
- 观众与房间维持 WebSocket 长连接，断线后能快速恢复
- 任一商品的新出价需要在秒级同步给房间内所有在线观众
- 每个商品有严格的生命周期和状态流转
- 成交后记录中标者信息

### 1.2 目标

构建一个支持多房间、每房间多商品同时拍卖的实时拍卖系统，满足：
- 一个房间支持多个商品同时竞拍，每个商品独立出价、独立落槌
- 每个观众与房间维持独立 WebSocket 长连接
- 断线后快速重连，恢复房间状态和最新出价，观众无卡顿体验
- 最新出价秒级同步给房间内所有在线观众
- 并发出价不串价
- 拍卖状态严格可控

## 2. 用户角色

| 角色 | 职责 | 派生规则 | 典型操作 |
|---|---|---|---|
| 卖家 | 创建房间、创建拍卖商品、设置起拍价和规则 | 商品的创建者自动成为该商品的卖家；房间的创建者可管理房间内的商品 | 创建房间、创建商品、查看自己创建的商品、查看拍卖结果 |
| 观众/买家 | 进入房间观看多个商品拍卖，可对任意商品出价 | 所有用户均可进入任意房间观看；对商品出价时成为该商品的买家 | 加入房间、查看房间内商品列表、出价、查看出价历史 |
| 系统拍卖师 | 控制每个商品自动开始和自动结束 | 由系统定时任务扮演，无需对应用户身份 | 到达 start_time 自动开启商品、到达 end_time 自动落槌 |

> 本项目为训练项目，用户身份通过 `X-User-Id` 请求头模拟，不做真实身份认证与权限管理。角色由业务规则派生，不在请求头中显式传递。

## 3. 功能需求

### 3.1 房间管理

房间是观众加入和广播的基本单位，一个房间内可同时存在多个商品。

| 编号 | 需求 | 优先级 |
|---|---|---|
| R1.1 | 卖家可创建房间，设置房间名称和描述 | P0 |
| R1.2 | 用户可查询房间列表，支持分页 | P0 |
| R1.3 | 用户可查询房间详情，包含房间内商品概要 | P0 |
| R1.4 | 房间创建后处于"营业中"状态，可被观众加入 | P0 |

**房间核心字段：**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | 业务 ID | 全局唯一 | 房间唯一标识 |
| name | 字符串 | 必填，长度 1-128 | 房间名称 |
| description | 字符串 | 可选，长度 0-2048 | 房间描述 |
| owner_id | 用户 ID | 必填 | 房间创建者 |
| status | 枚举 | 必填 | 房间状态：online |
| created_at | 时间戳 | 必填 | 创建时间 |
| updated_at | 时间戳 | 必填 | 最后更新时间 |

### 3.2 商品管理

商品是拍卖的最小单元，每个商品属于且仅属于一个房间。

| 编号 | 需求 | 优先级 |
|---|---|---|
| I2.1 | 卖家可在指定房间内创建拍卖商品，设置标题、描述、起拍价、最小加价幅度、开始时间、结束时间 | P0 |
| I2.2 | 用户可查询房间内商品列表，支持按状态筛选和分页 | P0 |
| I2.3 | 用户可查询商品详情，包含当前状态、当前最高价、出价次数等 | P0 |
| I2.4 | 商品创建后处于"待开始"状态，到达开始时间后自动进入"进行中"状态 | P0 |
| I2.5 | 商品到达结束时间后自动落槌 | P0 |
| I2.6 | 商品创建后、开始时间之前，卖家可删除该商品；开始后不可删除 | P1 |

**商品核心字段：**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | 业务 ID | 全局唯一 | 商品唯一标识 |
| room_id | 业务 ID | 必填 | 所属房间 |
| title | 字符串 | 必填，长度 1-128 | 商品标题 |
| description | 字符串 | 可选，长度 0-2048 | 商品描述 |
| start_price | 整数（分） | 必填，≥ 1 | 起拍价，以分为单位 |
| min_increment | 整数（分） | 必填，≥ 1 | 最小加价幅度，以分为单位 |
| start_time | 时间戳 | 必填，必须早于 end_time | 拍卖开始时间 |
| end_time | 时间戳 | 必填，必须晚于 start_time | 拍卖结束时间 |
| seller_id | 用户 ID | 必填 | 创建者，即卖家 |
| status | 枚举 | 必填 | 商品状态，见 §6.1 |
| current_price | 整数（分） | 必填，默认 0 | 当前最高价，0 表示尚无有效出价 |
| winner_id | 用户 ID | 可选 | 中标者，落槌后填充 |
| bid_count | 整数 | 必填，默认 0 | 有效出价次数 |
| created_at | 时间戳 | 必填 | 创建时间 |
| updated_at | 时间戳 | 必填 | 最后更新时间 |

### 3.3 实时出价

| 编号 | 需求 | 优先级 |
|---|---|---|
| B3.1 | 观众可通过 WebSocket 加入指定房间，连接建立后收到该房间内所有商品当前状态快照 | P0 |
| B3.2 | 观众在商品"进行中"状态下可对该商品出价；非进行中状态出价被拒绝 | P0 |
| B3.3 | 首次有效出价必须大于等于起拍价；后续有效出价必须大于等于当前最高价加最小加价幅度 | P0 |
| B3.4 | 出价过低时系统拒绝并返回明确错误码与提示 | P0 |
| B3.5 | 同一观众对同一商品两次出价间隔不得小于 2 秒 | P0 |
| B3.6 | 出价成功后，该商品所在房间内所有在线观众实时收到最新价格和出价人信息 | P0 |
| B3.7 | 出价成功后，系统记录一条出价日志 | P0 |

**出价记录核心字段：**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | 业务 ID | 全局唯一 | 出价记录唯一标识 |
| item_id | 业务 ID | 必填 | 所属商品 |
| bidder_id | 用户 ID | 必填 | 出价人 |
| amount | 整数（分） | 必填，≥ 1 | 出价金额 |
| bid_time | 时间戳 | 必填 | 出价时间 |

### 3.4 出价历史

| 编号 | 需求 | 优先级 |
|---|---|---|
| H4.1 | 任何用户均可查询指定商品的出价历史 | P0 |
| H4.2 | 出价历史按出价时间倒序排列 | P0 |
| H4.3 | 出价历史支持游标分页，默认每页 20 条，最大每页 100 条 | P0 |

### 3.5 落槌与成交

| 编号 | 需求 | 优先级 |
|---|---|---|
| A5.1 | 商品到达结束时间后自动落槌 | P0 |
| A5.2 | 落槌时若存在有效出价，商品状态变为"已成交"，最高价出价人成为中标者 | P0 |
| A5.3 | 落槌时若不存在有效出价，商品状态变为"流拍" | P0 |
| A5.4 | 落槌后向该商品所在房间内所有在线观众广播落槌结果 | P0 |
| A5.5 | 落槌后不允许再对该商品出价 | P0 |

### 3.6 心跳与连接管理

| 编号 | 需求 | 优先级 |
|---|---|---|
| C6.1 | WebSocket 连接支持心跳保活，客户端每 30 秒发送一次心跳，服务端 60 秒未收到心跳视为断线 | P1 |
| C6.2 | 用户主动关闭连接、心跳超时或网络异常导致连接断开时，均从房间在线列表移除 | P0 |
| C6.3 | 一个用户同一时刻在同一房间内只保留一个 WebSocket 连接；新连接建立时踢掉旧连接 | P0 |

### 3.7 断线重连

| 编号 | 需求 | 优先级 |
|---|---|---|
| REC7.1 | 观众断线后重新建立 WebSocket 连接并重新加入同一房间 | P0 |
| REC7.2 | 重连成功后，服务端向该观众推送房间内所有商品当前状态快照 | P0 |
| REC7.3 | 重连期间错过的历史出价不同步，观众以当前状态快照为准 | P1 |
| REC7.4 | 重连过程观众感知无明显卡顿，从建连到收到状态快照时间小于 1 秒 | P1 |

### 3.8 WebSocket 事件

PRD 定义事件类型与方向，具体消息字段见 `api/openapi.yaml`。

| 事件 | 方向 | 说明 |
|---|---|---|
| join | Client → Server | 加入指定房间 |
| ping | Client → Server | 心跳请求 |
| pong | Server → Client | 心跳响应 |
| bid | Client → Server | 对指定商品提交出价 |
| bid_update | Server → Client | 某商品有新出价时，向房间内所有在线观众广播最新价格和出价人 |
| hammer | Server → Client | 某商品落槌时，向房间内所有在线观众广播结果 |
| item_state | Server → Client | 向单个观众推送商品当前状态快照 |
| room_state | Server → Client | 向单个观众推送房间内所有商品当前状态快照 |
| error | Server → Client | 业务错误或协议错误 |

## 4. 非功能需求

### 4.1 性能

| 指标 | 目标 | 测量边界 |
|---|---|---|
| 单商品出价接口 QPS | ≥ 5,000 | 单实例，REST 出价接口，并发连接 1,000，失败率 < 0.1% |
| 出价 P99 延迟 | < 50ms | 服务端处理耗时，不含网络传输 |
| WebSocket 推送延迟 | < 1s | 从服务端收到出价到向该商品所在房间内所有在线观众推送完成，单房间在线人数 ≤ 1,000 |
| 断线重连恢复时间 | < 1s | 从 WebSocket 建连完成到观众收到 room_state 快照 |
| 并发出价一致性 | 100% | 100 并发用户同时向同一商品出价后，系统记录的最高价等于实际最高出价 |

### 4.2 可靠性

- 每条成功出价最终都写入持久化出价记录
- 落槌事件不丢失，所有"进行中"状态的商品最终都会落槌
- 观众断线后重连能正确恢复房间状态快照

### 4.3 可扩展性

- 支持多实例水平部署
- 房间内广播支持跨实例推送
- 一个房间可同时存在多个商品，商品之间状态独立

### 4.4 可观测性

- 请求日志带请求 ID
- 核心指标可监控：QPS、延迟、WebSocket 连接数、房间在线人数、消息队列堆积、慢请求

## 5. 边界与限制

| 范围 | 说明 |
|---|---|
| 认证授权 | 使用 `X-User-Id` 请求头模拟用户，不做真实登录和 RBAC |
| 角色派生 | 商品创建者为卖家，房间创建者可管理房间内商品，其他用户为观众/买家 |
| 支付结算 | 本期不做支付结算，落槌成交为终态 |
| 图片/文件 | 商品图片仅支持 URL，不上传文件 |
| 保留价 | 不支持保留价，只要有人出价且满足起拍价即有效 |
| 延时周期 | 不支持延时周期，到达结束时间即落槌 |
| 手动落槌 | 不支持人工提前落槌，仅支持系统自动落槌 |
| 多端同步 | 一个用户在同一房间内同时只支持一个 WebSocket 连接，新连接踢掉旧连接 |
| 重连补发 | 断线期间的历史出价不同步，仅以状态快照恢复 |
| 货币 | 所有金额以人民币"分"为单位，整数存储 |
| 商品编辑/删除 | 商品开始时间之前卖家可删除；开始后不可编辑、不可删除 |
| 房间删除 | 本期不支持删除房间 |

## 6. 术语表

### 6.1 商品状态

| 状态 | 说明 |
|---|---|
| 待开始（pending） | 商品已创建，尚未到达开始时间 |
| 进行中（live） | 已到达开始时间，可以接受出价 |
| 落槌中（closing） | 已到达结束时间，正在执行落槌逻辑 |
| 已成交（sold） | 落槌完成，存在有效出价，已记录中标者 |
| 流拍（failed） | 落槌完成，无有效出价 |

### 6.2 状态转移矩阵

| 当前状态 | 可转移状态 | 触发事件 |
|---|---|---|
| pending | live | 到达 start_time |
| live | closing | 到达 end_time |
| closing | sold | 存在有效出价 |
| closing | failed | 无有效出价 |

### 6.3 通用术语

| 术语 | 说明 |
|---|---|
| 房间 | 观众加入和广播的基本单位，一个房间可同时存在多个商品 |
| 商品 | 拍卖的最小单元，属于一个房间，有独立计时和状态 |
| 拍卖会 | 泛指商品拍卖活动，本系统中一个商品即对应一场拍卖 |
| 落槌 | 商品拍卖结束，确定成交或流拍 |
| 流拍 | 商品拍卖结束但无人出价 |
| 起拍价 | 商品开始时的最低可接受首次出价 |
| 最小加价幅度 | 新出价必须比当前最高价高出的最小金额 |
| 当前最高价 | 商品进行中当前最高的有效出价 |
| 有效出价 | 满足商品状态、起拍价/加价幅度、限流规则的出价 |
| 出价过低 | 首次出价低于起拍价，或后续出价低于当前最高价加最小加价幅度 |
| 中标者 | 落槌时出价最高的买家 |
| 出价历史 | 一个商品所有有效出价的记录 |
| 心跳 | WebSocket 连接保活机制 |
| 在线用户 | 当前已建立 WebSocket 连接并加入房间的用户 |
| 状态快照 | 房间内所有商品当前状态的完整视图 |

## 7. 验收标准

### 7.1 功能验收

#### AC-1：创建房间
- **Given**：卖家使用有效 `X-User-Id` 请求头
- **When**：提交房间名称和描述
- **Then**：系统创建房间，返回房间 ID，房间状态为"营业中"

#### AC-2：创建商品
- **Given**：卖家已创建房间
- **When**：在房间内提交标题、起拍价、最小加价幅度、开始时间、结束时间
- **Then**：系统创建商品，返回商品 ID，初始状态为"待开始"

#### AC-3：商品自动开始
- **Given**：一个状态为"待开始"的商品
- **When**：当前时间到达开始时间
- **Then**：该商品状态自动变为"进行中"

#### AC-4：WebSocket 加入房间与心跳
- **Given**：一个"营业中"的房间，房间内存在"进行中"商品
- **When**：观众通过 WebSocket 发送 join 事件加入房间，并周期性发送 ping
- **Then**：连接保持，服务端回复 pong，房间内在线人数包含该观众，观众收到 room_state 快照

#### AC-5：多商品同时拍卖
- **Given**：一个房间内有商品 A 和商品 B 同时处于"进行中"状态
- **When**：观众对商品 A 出价
- **Then**：商品 A 当前最高价更新，商品 B 不受影响，房间内所有在线观众收到商品 A 的 bid_update 事件

#### AC-6：有效出价成功
- **Given**：一个"进行中"的商品，起拍价 1000 分，最小加价幅度 100 分
- **When**：观众出价 1000 分（首次）或出价大于等于当前最高价 + 100 分（后续）
- **Then**：出价被接受，商品当前最高价更新，房间内所有在线观众收到 bid_update 事件

#### AC-7：过低出价被拒绝
- **Given**：一个"进行中"的商品，当前最高价 1000 分，最小加价幅度 100 分
- **When**：观众出价 1050 分
- **Then**：出价被拒绝，返回错误码，房间内不广播该出价

#### AC-8：限流
- **Given**：一个"进行中"的商品
- **When**：同一观众在 2 秒内对该商品连续出价两次
- **Then**：第二次出价被拒绝，提示出价过于频繁

#### AC-9：落槌成交
- **Given**：一个"进行中"的商品，已有有效出价
- **When**：到达结束时间
- **Then**：状态变为"已成交"，最高价出价人成为中标者，房间内广播 hammer 事件

#### AC-10：落槌流拍
- **Given**：一个"进行中"的商品，无任何有效出价
- **When**：到达结束时间
- **Then**：状态变为"流拍"，房间内广播 hammer 事件

#### AC-11：断线重连
- **Given**：一个观众已加入房间并在线
- **When**：该观众断开连接后重新建立 WebSocket 连接并重新 join 同一房间
- **Then**：旧连接被清理，新连接在 1 秒内收到 room_state 快照，快照中包含房间内所有商品最新状态

### 7.2 性能验收

#### AC-12：单商品出价性能
- **Given**：单实例部署，1000 并发连接
- **When**：持续向单个商品的 REST 出价接口发送请求
- **Then**：QPS ≥ 5,000，P99 服务端处理延迟 < 50ms，失败率 < 0.1%

#### AC-13：房间内广播性能
- **Given**：一个房间有 1,000 个在线观众，房间内同时有 5 个商品进行中
- **When**：持续对其中任意商品出价
- **Then**：房间内所有在线观众在 1 秒内收到 bid_update 事件，系统整体稳定

### 7.3 可靠性验收

#### AC-14：并发出价一致性
- **Given**：100 个并发用户同时向同一商品出价
- **When**：出价全部处理完成
- **Then**：系统记录的最高价等于实际最高出价，出价记录数等于成功出价次数

#### AC-15：落槌不遗漏
- **Given**：存在多个"进行中"商品，分布在不同房间
- **When**：每个商品到达结束时间
- **Then**：所有商品最终都落槌，无遗漏

#### AC-16：断线不重号
- **Given**：一个观众在线并对商品出价成功
- **When**：该观众断线后重连
- **Then**：在线人数正确反映实际连接数，不会重复计数

### 7.4 一致性验收

#### AC-17：成交一致性
- **Given**：商品状态为"已成交"
- **When**：查询该商品详情
- **Then**：winner_id 与出价历史中的最高价出价人一致

#### AC-18：流拍一致性
- **Given**：商品状态为"流拍"
- **When**：查询该商品详情
- **Then**：winner_id 为空

#### AC-19：多商品隔离
- **Given**：同一房间内商品 A 已成交、商品 B 仍进行中
- **When**：查询房间详情
- **Then**：商品 A 状态为 sold，商品 B 状态为 live，两者 current_price/winner_id 互不干扰
